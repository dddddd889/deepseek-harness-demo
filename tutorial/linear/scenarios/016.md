## 同一次回复里的thinking、正文和工具调用，怎样拼到一起

**SSE只负责拆出事件；把这些事件拼成一条assistant消息的是本步的`DeepSeekModel.stream()`。**同一次HTTP请求里，thinking、正文和工具调用可以分别到达，也可以出现在同一条增量事件里。代码按字段分别收集，最后统一组装。

这里已经使用OpenAI兼容协议：推理放在`reasoning_content`字段，正文放在`content`字段，工具调用放在`tool_calls`字段。它们属于同一条assistant消息的不同字段，不是把几种内容混成一段文本，也不是Anthropic式的thinking内容块。

### 先沿一条具体回复走一遍

假设用户要求“计算2加3”，下表是同一个HTTP响应里的连续SSE数据。各条JSON都属于`choices[0]`，表中只展示关键字段；工具参数分片用JavaScript字符串写法展示。

| 依次收到的SSE数据 | 代码更新什么 | 累积结果 |
| --- | --- | --- |
| `delta.reasoning_content = "需要"` | `reasoning += ...` | 推理为“需要” |
| `delta.reasoning_content = "计算"` | 继续追加到同一个reasoning | 推理为“需要计算” |
| `delta.content = "我先算一下。"` | `content += ...`，同时产出text | 正文为“我先算一下。” |
| `delta.tool_calls`中工具index=0，id=`call-1`，name=`sum`，arguments片段为`'{"a":2,'` | 把身份、名称和参数分片放进`calls.get(0)`对应的对象 | 参数字符串暂时不完整，不能执行 |
| 同一工具index=0，arguments片段为`'"b":3}'` | 追加到该工具的json字符串 | 参数成为`{"a":2,"b":3}` |
| `finish_reason = "tool_calls"` | 保存到finish，仍继续接收 | 已知模型为什么停，还未确认数据发送完 |
| `usage`，同时`choices: []` | 产出usage，不新增回答内容 | 记录本次用量 |
| `[DONE]` | 设置ended并退出接收循环 | 开始完整性检查和最终组装 |

上面的中文推理和工具参数只是演示数据，便于观察拼接顺序，不代表真实模型一定按这些分片返回。同一个delta也可以同时携带多个字段；代码分别处理，不是互斥的`if/else`。

联系这些片段的关键，是变量在接收循环外创建：

```javascript
// 同一次请求一直复用这些累积变量；每次新请求会重新创建。
const calls = new Map()
let content = '', reasoning = '', sawReasoning = false, finish, ended = false
```

每处理完一条SSE事件，这些变量都还在。新片段继续追加进去，不会因为一条事件结束就清空。工具的Map按工具index分开保存参数，因此多个工具的分片交错到达，也不会拼到同一个参数字符串里。

### 两个index不是一回事

- `choice.index`：同一次请求里的第几份备选回答。本步只处理第0份，所以同一份回答的各个分片都使用`choice.index = 0`，不是每收到一片就加一。
- `delta.tool_calls[].index`：这份回答里的第几个工具调用。本步可以处理多个工具，用这个index分别累积它们的参数。

所以“一份回答中包含两个工具调用”是允许的，并不违反代码里的“只支持单个模型候选”。这里的“模型候选”就是备选回答，不是模型数量，也不是工具数量。

### 组装后的assistant长什么样

确认完整结束、校验工具身份、解析参数JSON之后，本步保存的`replay.message`会是这样的对象：

```json
{
  "role": "assistant",
  "reasoning_content": "需要计算",
  "content": "我先算一下。",
  "tool_calls": [
    {
      "id": "call-1",
      "type": "function",
      "function": {
        "name": "sum",
        "arguments": "{\"a\":2,\"b\":3}"
      }
    }
  ]
}
```

**推理、正文、工具调用都在同一条assistant消息里，各用自己的字段。**如果没有推理，省略`reasoning_content`即可，正文和工具调用仍可以在一起；只有正文时则不写`tool_calls`。有没有thinking不是判断工具调用的依据。

还要留意参数的两种形态：线上`function.arguments`是JSON字符串，适配器内部用`JSON.parse(call.json)`得到对象后，才以`kind: 'tool'`交给Loop。回放给模型时保存原参数字符串。

### 从适配器到下一次模型请求，谁负责什么

```mermaid
sequenceDiagram
    participant HTTP as 同一次HTTP响应
    participant SSE as sse解析器
    participant Model as DeepSeekModel.stream
    participant Loop as runTurn执行循环
    participant Tools as Tools执行入口
    HTTP->>SSE: 多块字节，包含多条SSE事件
    SSE->>Model: 逐条返回data字符串
    Model->>Model: 累积reasoning、content、calls
    Model-->>Loop: text片段收到就产出
    Note over Model: finish_reason先记住，DONE才退出接收
    Model->>Model: 校验完整结束，解析工具参数
    Model-->>Loop: thinking、tool、replay、finish各类Part
    Loop->>Loop: 保存一条message/assistant
    Loop->>Tools: execute或batch
    Tools-->>Loop: 工具结果
    Loop->>Loop: 追加独立的message/tool
    Loop->>Model: 下一次stream，传入最新历史
    Model->>Model: toMessages取replay.message还原assistant
```

有两次组装，分工不同：

1. `deepseek.mjs`把线上字段拼好，并通过replay保存完整的OpenAI兼容assistant消息。正文片段立即产出，thinking与工具调用等完整校验后再产出。
2. `loop.mjs`收集`partial、thinking、calls、replay`，一次性追加`message/assistant`到会话事实；工具执行结果随后以`message/tool`记录。

下一次请求时，`toMessages()`优先使用同协议的`replay.message`。历史里先是assistant提出调用，再是`role: tool`的执行结果；结果用`tool_call_id: "call-1"`关联原调用。工具结果不会塞回上一条assistant的正文或推理里。

## finish_reason和[DONE]，到底遇到谁才结束

**当前实现遇到`[DONE]`才退出接收循环；`finish_reason`只是先记住停止原因。**两者都收到后，还必须通过工具参数等检查，才能交付完整回复。

| 信号 | 表达什么 | 当前代码做什么 |
| --- | --- | --- |
| SSE空行，例如`\n\n` | 一条SSE事件结束 | 解析器产出这一条data，继续处理后面的事件 |
| `choice.finish_reason` | 这一份回答为什么停止生成 | 保存到finish，继续接收可能随后到达的usage |
| `data: [DONE]` | 该Chat Completions接口的发送结束标记 | 设置ended为true，break退出接收循环，再检查finish等信息 |

`[DONE]`由SSE解析器去掉`data:`前缀后返回，是一个普通字符串，不是JSON。因此代码在`JSON.parse(raw)`之前先判断它。

```text
收到finish_reason → 保存停止原因，暂不结束
收到usage         → 记录用量，继续接收
收到[DONE]        → 退出接收循环
                  → 检查finish_reason、工具身份与参数
                  → 组装完整assistant，产出finish
```

当前只允许停止原因之后再到达不含候选的用量事件（`choices: []`）；若之后又返回候选内容，会报“模型在finish_reason之后继续返回候选”。这避免把停止后的新内容悄悄接进已经结束的回答。

具体停止原因的后续行为：

- `tool_calls`：必须有工具调用，适配器转换成`finish: tools`，Loop执行工具后继续下一step。
- `stop`：正常完成当前回复；没有工具调用时，Loop结束当前turn。
- `length`：保留长度截断含义，Loop以length结束，不冒充正常完成。本步若同时收到工具调用但停止原因不是tool_calls，会拒绝交付这些调用。
- 其他原因：本步按异常处理，不统一伪装成stop。

只有finish_reason、没有[DONE]就断流，或者只有[DONE]、没有finish_reason，都会报“模型消息未完整结束”。已显示的正文不等于完整回复已经提交；出现异常或取消时，Loop会把已收到的非空正文记为`interrupted: true`，不会据此执行未完成校验的工具调用。

## 会不会把两次请求的响应拼到一起

**会跨同一个响应里的多条SSE事件累积，不会拿下一次HTTP响应来补上一次没收完的回复。**

```text
请求A → 多条SSE事件 → 一条assistant消息
                            ↓
                       执行工具、记录tool结果
                            ↓
请求B → 新的累积变量 → 下一条assistant消息
```

一次turn可以包含请求A和请求B，但每次`stream()`的reasoning、content、calls和SSE解析器的buffer都是独立创建的。跨请求传递的是已保存的历史消息；前一次缺少结束信息就报错，不会自动把两条响应流接起来。

## 用VS Code核对，而不是只记结论

完成下文文件后，在自己的工程里打开`tests/016-deepseek.test.mjs`，选择“Bun：当前测试”，按F5。给`src/deepseek.mjs`中的三个位置设置断点：

3. `const message = { role: 'assistant', content }`：检查reasoning、parsed以及随后生成的message。走到这里时，结束信息和工具参数已经校验通过。

继续到Loop追加`message/assistant`的位置，观察thinking、calls和replay如何放在同一条会话记录里；在两次请求贯通测试中，再到`toMessages()`检查下一次请求是否同时带有assistant的reasoning_content、tool_calls，以及后面的tool结果。
