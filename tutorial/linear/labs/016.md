## 固定解析通过后，再做真实 API 验收

先保留上面的确定性测试结果，再在 PROJECT 执行：

```sh
cp .env.example .env
```

用编辑器打开 PROJECT/.env，把 `DEEPSEEK_API_KEY` 填成你自己的可用 Key。不要把 Key 放进源码、聊天记录或 LEARNING.md。真实请求会消耗你的额度。随后执行：

```sh
bun --env-file=.env src/live-demo.mjs "调用 sum 计算 2 加 3，最后只输出结果"
```

本步固定使用OpenAI兼容接口，`.env`配置如下；Key继续只在本机填写：

```dotenv
DEEPSEEK_API_KEY=
DSH_MODEL=deepseek-flash
DEEPSEEK_BASE_URL=https://api.deepseek.com
```

实际请求为`POST https://api.deepseek.com/chat/completions`，鉴权使用`Authorization: Bearer ...`。如果自己的兼容网关根地址已经包含`/v1`，代码会保留它并追加`/chat/completions`，不会重复添加`/v1`。这里不是只换URL：请求体、工具定义、工具回复和流解析也已改成Chat Completions格式。[DeepSeek官方调用示例](https://api-docs.deepseek.com/zh-cn/)

必须观察到`request/start → message/assistant（含calls）→ tool/start → message/tool → 第二次request/start → 最终message/assistant → turn/end`。模型实际返回的工具调用和完成原因以日志为准；缺Key时入口直接失败，固定模型或本地回声不算真API通过。HTTP 401/429、模型不存在、网关协议不兼容时，记录第一条真实错误。

流里每条JSON读取`choices[0].delta`：`content`是正文，`reasoning_content`是推理，`tool_calls`按index拼接工具参数字符串。收到`finish_reason`后还会等待`data: [DONE]`，缺少任一结束信息都报错；`tool_calls`才转换成Loop所需的`finish: tools`，`stop`和`length`分别保留正常停止与长度截断含义。[Chat Completions字段](https://api-docs.deepseek.com/api/create-chat-completion/)

本步把完整assistant消息保存在replay里，工具续轮时带回`reasoning_content`与原工具调用，工具结果使用`role: tool`和`tool_call_id`关联。DeepSeek在携带工具的请求中要求回传历史推理内容。[推理回传规则](https://api-docs.deepseek.com/guides/thinking_mode/)

这一步的真请求记录只证明当前路由，不证明 Files、其他 provider、长上下文和线上失败策略全都通过。后面的 `bun test` 仍运行固定模型与固定 HTTP 正文。

第017步的Files模块仍是另一个协议示例，保留原有Anthropic式请求头，尚未接入本步的Chat Completions消息；不能只把它的root换成这里的根地址，就认定文件上传也兼容。
