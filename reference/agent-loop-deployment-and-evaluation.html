AGENT LOOP · DEPLOYMENT & EVALUATION

Loop 放在哪，
怎样执行、恢复和评估？

本地 Loop 便于使用个人环境，云端 Loop 便于持续调度和跨设备协作。两者都能评估，关键是保留实际模型输入、执行事实和结果证据；混合架构还要把两端记录接起来。

先拆开三个位置：模型生成下一步动作；Loop 负责上下文、请求、调度和停止；工具执行器实际访问文件、进程与服务。云端模型不代表云端 Loop，本地工具也不证明 Loop 在本机。

核对日期：2026-10-16。Harness 依据本地子模块 99f6f02fecdb7dff40c3fbc9470f5907c29f74ca；OpenHands 指当前 Software Agent SDK，排除旧 V0；Codex 按执行模式区分。下方设备网关、远程调用状态和评估证据清单均为设计建议，本次没有实现远程执行协议，也没有运行生产会话评测。

用有状态 Game Server 理解 AI Workspace

Agent 改了三个文件、启动测试，用户关闭页面后再回来，希望能继续工作。这像玩家重新上线回到同一个世界：连接可以更换，已经发生的事实和产物需要保留。

游戏概念AI 工作空间职责
世界与存档持久状态与产物保存目标、约束、会话事件、操作进度及文件版本。
游戏引擎Runtime / 会话编排与执行服务驱动 Agent、执行工具，处理权限、取消与恢复。
玩家或 NPC 控制逻辑Agent根据当前事实决定下一步，保存继续任务所需信息。
客户端画面UI 投影展示状态；页面断线不自动表示后端停止。

三种恢复分别判断：会话从持久状态重建；文件依赖持久存储或快照；进程需要执行器查询与接管能力。Event Log 不会自动还原旧调用栈、丢失的磁盘或已经发生但未回写的外部副作用。

多 Agent 共享目录时，先串行写入或使用独立 worktree，再合并结果；事件版本号不能阻止 Shell 互相覆盖文件。这个类比说明逻辑职责，不要求固定 Tick、每个工作区常驻一个进程，或每个模块独立部署。

OpenHands V1 中，Conversation 编排，ConversationState 与 EventLog 保存会话状态及历史，Workspace 抽象执行环境，Agent Server 提供远程服务。这里的 Workspace 比产品层“整个工作空间”的含义更窄。以上并发与恢复方案属于设计建议。

本地与云端：主要改变运行方式

维度本地 Loop云端 Loop
个人环境直接使用本地代码、依赖、内网和已授权登录态。重建云端环境，或连接本地执行器。
持续运行与多设备受电脑休眠和进程退出影响；跨设备需要连接或同步。便于后台调度与共享会话，但需要持久化、身份和并发控制。
工具延迟本地调用无需跨网往返。调用本地工具要经过网络；频繁小调用尤其明显。
运维与成本维护客户端版本、兼容性，使用个人电脑资源。集中升级，同时承担服务、存储、带宽与租户隔离。
数据边界日志可留本地，但云端模型仍会收到请求中的上下文。上下文与工具结果通常经过云端，需要限定上传范围。

Loop 通常主要做编排和 I/O，GPU 推理由模型服务承担。把 Loop 搬到云端，不直接让模型变快或更聪明。云端的故障恢复也不是自动获得的能力。

Mac 休眠的例子：云端 Loop 可以保留进度、做不依赖 Mac 的步骤，但本地工具离线后，仍然不能继续修改 Mac 上的项目。“云端 Loop＋本地工具”不具备全云端执行的持续可用性。

混合架构：本地主动连接，云端下发调用

  1. 本地常驻执行器认证后主动连接云端，登记设备、工作区和允许使用的能力。
  2. 云端 Loop 请求模型，将返回的工具名称与参数写入调用记录，通过网关派发。
  3. 本地再次校验权限，记录状态、执行工具，保存输出与终态，再回传结果。
  4. 云端关联原调用并持久记录模型可见结果，然后继续请求模型。

协议至少区分稳定的逻辑调用 ID 与每次投递的尝试 ID，携带会话、设备、工作区、截止时间与权限上下文。路由身份必须经过认证和授权。本地执行器不必自己再跑一套模型循环。

断线、取消和权限：超时不等于没执行

场景判断处理
设备离线，尚未派发未执行等待、超时或拒绝；过期请求不能在上线后突然执行。
已发送，没有确认接收与执行情况未知按调用 ID 查询和对账，不直接重跑。
执行完成，结果回传失败本地若已保存结果，可恢复证据补传原结果，去重结算。
副作用发生、结果落盘前崩溃结果未知查询外部状态；使用业务幂等键，不能盲目重试写操作。
取消、超时、旧执行者重连意图和实际终态需要分开处理子进程、确认终态、检查所有权代次；迟到结果不能覆盖新尝试。

仅靠重试和调用去重，不能承诺任意 Shell 命令恰好执行一次。网络断开不证明进程停止，取消也不自动回滚已经完成的写操作。

可控复现：在本地测试正常退出且结果已保存、尚未回传时断网；重连应补传同一调用的原结果。再在副作用完成、执行记录持久化之前终止执行器，应出现“结果未知”，而不是伪造成功或未执行。

本地限定目录、命令和能力；审批绑定具体调用与参数。来自云端的请求仍需校验，工具输出按不可信数据处理。凭证留在本机使用，也要避免通过日志与输出泄漏。

Skill：三种架构怎样加载、读取引用和执行脚本？

Skill 需要可访问，不要求整个目录都下载到 Loop 宿主。说明与引用要能读给负责决策的 Agent；脚本、模块、模板与依赖要能由对应执行器使用。两端同机时安装在一起最直接，混合架构则可以通过连接器读取和执行。

check-project/
├── SKILL.md                  使用条件与流程
├── references/
│   ├── rules.md              检查规则
│   └── repair-guide.md       修复说明
├── scripts/
│   ├── check.py              检查入口
│   ├── repair.py             修复入口
│   └── helpers.py            公共模块
└── assets/
    └── report-template.md    报告模板

例如流程要求“先读规则、运行检查，发现问题再读修复说明并修复”。Agent 先发现 skill 名称和描述，选择后加载正文，再按需读引用、调用脚本；选中 skill 不等于执行全部脚本，链接存在也不等于引用已进入上下文。

阶段本地 Loop＋本地工具云端 Loop＋云端工具云端 Loop＋本地工具
资源准备与发现本机安装或从仓库发现，生成可用摘要。云端检出、安装或挂载资源，生成摘要。可完整留在本机；连接器上报获准可见的摘要、版本和设备关联。
加载 SKILL.md本地读取正文，交给 Loop 使用。读取云端可访问的正文，交给 Loop 使用。云端经连接器请求本地正文，内容回传到云端上下文。
读取引用 Markdown按 skill 资源基底读取选中的本地文件。按云端资源基底读取；URL 等资料经资源接口获取。经连接器按 skill 身份、版本和相对路径读取；本地绝对路径不能直接在云端打开。
执行脚本本机解释器运行脚本，使用本机依赖和目标项目。云端进程运行脚本，使用云端依赖和工作区。本地进程运行；脚本、公共模块、模板和凭证可以留本机，结果回传云端。
容易缺失的条件模块、运行时、路径或本地权限。仅同步正文，漏掉引用、模块和模板；环境版本不一致。设备离线、两端版本不一致、资源不可达、重复执行与结果补传。

Markdown 和源码的作用不同：读取规则后，规则内容可能进入模型上下文。执行 check.py 时，Python 可以自行导入 helpers.py、读取模板，模型未必看过这些文件全文；它通常先看到执行结果。即使 Loop 在本地，调用云端模型时，请求中包含的说明和引用内容仍会上传。

混合架构的完整一条路径

本地登记 skill 摘要与固定版本
  → 云端选择 skill
  → 经连接器读取本地 SKILL.md
  → 按需读取本地 references/rules.md
  → 请求本地执行 scripts/check.py，明确目标工作区
  → 本地进程加载公共模块、模板并完成检查
  → 保存并回传结果
  → 云端决定是否读取修复指南，执行修复与复查

这是建议的本地资源代理方案，不要求本地再跑一个模型 Loop。也可以同步说明到云端、脚本留本机，但必须让说明与脚本使用同一资源版本。Markdown 内容上传与整个 skill 包下载到云端磁盘是两回事。

路径、分发和版本要分别明确

  • Skill 根与项目根分开：前者定位说明、脚本和模板，后者定位要操作的项目；不要依赖偶然的 cwd 或作者电脑上的绝对路径。
  • 引用按来源解析：目录、URL、提供方管理的资源使用各自读取机制。云端能读某份资源，不表示本地脚本也能访问；需要另行同步或传入内容。
  • 分发覆盖实际依赖：安装、挂载或资源服务都可以，但不能只复制 SKILL.md。保留脚本需要的公共模块、模板、运行时与第三方依赖，凭证通过执行环境注入。
  • 版本与证据固定：记录实际读取的文件、实际执行的脚本、资源快照、环境、参数、设备与产物。仅有名称或无法取回内容的哈希，不够重建评估证据。

具体失败：云端新版说明要求新增参数，本地旧脚本却不支持。保持两端版本不一致即可复现；应由资源版本固定或能力校验提前暴露问题，不能事后简单归为模型能力差。

当前 Harness 已区分 skill 来源与资源基底，但文件系统提供方会在后续加载时重新读取正文；目录摘要不是完整资源包的版本锁。本地设备资源代理与不可变多文件快照需要另外实现。

会话评估：把决策、执行、传输与交付接起来

本地 Loop 需要持久记录和可靠补传；云端 Loop 易集中收集，但不会自动知道本机的真实执行结果。评估器可以独立部署，部署位置不决定判断能力。

模型正确选择测试命令 → 本地测试通过 → 回传断线 → 云端超时

模型决策：可以正确
本地执行：拿到可验证证据后，才能确认通过
用户交付：超时、未收到结果，仍然未完成或失败
结果声明：缺少证据却声称通过，需要另外检查

不要把网络失败直接当成模型选错工具，也不要从端到端产品统计中删除这次失败。权限拒绝、设备离线、取消与命令错误应记录各自原因。

证据层需要保存为什么
关联身份会话、Turn、Step、Trace、调用、尝试、设备、工作区与所有权代次。连接两端证据，识别重投与迟到结果。
模型输入实际上下文或可重建引用、工具 schema、模型配置、Prompt 与 Harness 版本。判断当时信息条件下的决策；保留压缩前日志和压缩后输入。
执行与产物本地状态、退出码、输出、权限决定、文件 diff、测试报告、外部回执。区分“调用返回成功”和“用户目标实际达成”。
环境与评估快照初始文件、未提交改动、依赖、各流游标、缺失项、脱敏 / 截断策略、评估版本。使实验可比较，结论可以追溯到固定证据。

跨端按因果关系、调用 ID 和每流序号关联，不按上传到达顺序排序，也不假设时钟一致。迟到证据生成新的评估修订，保留旧报告与原先等待超时的事实；缺失证据标记不可核验，不靠 Judge 猜。

OTel / Langfuse 是观测和评估副本，不能替代 canonical Session 日志和本地执行记录。Session ID 分组不会自动把所有执行数据交给评估器，应用需要显式提供所需证据。

耗时分别看模型请求、网络、本地排队与执行、审批和重连；并发时不能直接累加子调用耗时。各端内部用单调时钟计时，端到端时间从统一观察点测量。模型比较控制环境和预算，产品比较保留真实等待与交付失败。

历史回放、决策评估与行为重跑

目的所需输入边界
历史回放原始事件、模型输出、工具调用与结果。还原已记录的事实；日志不能单独证明外部状态。
评估当时决策模型当时实际看见的上下文、工具与权限。不把未来信息倒灌给当时的模型。
换模型 / Prompt 重跑初始工作区、依赖、权限、可控外部服务和相同预算。新行为可能走新路径；不能机械复用旧工具结果，也不能重放生产写操作。

固定工具结果回放适合检查原路径上的局部行为。完整行为比较需要可交互环境，或能覆盖新调用的模拟器。文件已被修改、未提交改动丢失、附件仅留哈希，都会破坏复现条件。

先人工检查真实会话中的失败与证据缺口，再确定自动评估范围。退出码、超时等已有确定事实可以直接统计；是否满足用户要求，需要匹配的结果证据与验收标准。

Harness：复用 Loop，在能力边界接入

第一版建议在云端 ctx.tools 注册工具代理，经网关调用本地执行器；需要复用上层文件、Shell 和终端工具时，再实现远程 ctx.fs / ctx.subprocess 提供方，并覆盖 PTY、取消、临时文件与附件等边界。

仓库 E2B POC 展示了执行环境与 Loop 可分离，不是已有本地设备连接方案。MCP 可复用工具发现与调用，但设备可达性、认证、路由、补传和副作用对账仍由宿主解决。云端不能直接访问另一台电脑的 localhost 或 stdio。
