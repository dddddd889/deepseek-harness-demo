先看全貌：一次追加，多个消费者

session.append() 复制并冻结数据，分配 Session 内连续的 seq，记录时间，再追加到内存日志。提交后通过 Cordis 的 session/event 通知消费者。观察者失败不会撤销已提交事件。

内存追加成功还不等于落盘。持久化消费者会缓冲并批量写入，session/flush 是等待持久化消费者排空的检查点。遥测入队也不等于 Collector 已保存。

用户：“读一下 config.json，解释里面的配置。”
  turn/start → step/start → user/message → request/header
  → assistant/chunk × N → assistant/message（含 tool-call 块）
  → tool/call → tool/result → step/end
  → step/start → assistant/chunk × N → assistant/message（解释正文）
  → step/end → turn/end

这是典型成功路径；零步结束、重试、取消、压缩会产生其他分支。

Session.append 与 deriveMessages · Agent Loop 的事件生产位置

“有多少层 type”：按职责分成 8 类

这些是帮助阅读源码的类型家族。同一个 Message 对象可以嵌在事件中，投影值也可以直接跨传输和客户端复用；不需要每过一层都重新造一套业务字段。

类别实际类型 / 标签负责什么与下一步的关系
① 会话事件SessionEventMap、SessionEvent<T>、SessionHeader记录顺序、时间、事实、Surface 操作和来源。各分支共同的输入；Header 保存会话级元数据。
② 模型中立消息Message、ContentBlock；流式阶段用 StreamChunk表达用户、助手、工具结果，以及文本、思考、工具调用等内容。Surface 选出消息事件，deriveMessages() 取出消息。
③ 模型厂商协议DeepSeek WireMessage、WireToolCall符合模型 API 的字段与 role 规则。适配器序列化模型中立消息；不是直接把 Event 发给模型。
④ UI 传输协议MuxFrame、ToolEventView；session/event、session/projection把事件或完成的投影值传到客户端。传输帧可以包裹事件，帧 type 和事件 type 各司其职。
⑤ UI 读模型ConversationViewNode、SessionProjectionMap、具体气泡/工具卡片节点描述当前要显示什么。聊天轨迹在客户端组装；领域状态在服务端折叠后推送。
⑥ 存储记录StorageRecord = SessionEvent | ChunkRow；另有 header 行无损保存事件，支持连续 chunks 打包和压缩。读取并解码后还原 SessionEvent；SQLite 使用自己的后端格式。
⑦ 逻辑遥测记录SessionTelemetryRecord按观测策略筛选，携带 channel、severity、attributes、body。经过复制、部署方脱敏，再交给遥测后端。
⑧ OTel 标准记录OTel LogRecord / OTLP Logs使用标准日志字段，交给 SDK 批处理和导出。进入 Collector 或日志平台；不负责 Session 恢复。
模型分支：SessionEvent → Surface → Message → WireMessage
聊天分支：SessionEvent → MuxFrame → ConversationViewNode → 组件
状态分支：SessionEvent → 领域投影值 → session/projection 帧 → Store → 组件
存储分支：SessionEvent ↔ StorageRecord ↔ JSONL / Zstd
遥测分支：SessionEvent → SessionTelemetryRecord → OTel LogRecord

上面的 Surface、Store、组件分别是选择结果、客户端状态容器和渲染单元，不额外凑成“第九、第十层 type”。划分的依据是数据的职责，不是所有 TypeScript 声明的总数。

一个 JSON 内为什么会出现好几个 type？

看这条通过 UI 通道发送的流式事件。三个 type 分别回答“传什么”“发生什么”“分片怎么更新”。

{
  "type": "session/event",           // 传输帧：里面是一条会话事件
  "sessionId": "session-demo",
  "event": {
    "type": "assistant/chunk",       // 事件：模型输出了一个流式分片
    "seq": 7,
    "time": 1792108800000,
    "data": {
      "turn": 1,
      "step": 1,
      "chunk": {
        "type": "text-delta",        // 分片：追加文本
        "index": 0,
        "text": "我先读取配置。"
      }
    }
  }
}
// JSONC 示意；真实 JSON 不包含这些中文注释。
判别字段例子不要混淆
帧 typesession/event、session/projection网络消息类别，不是领域事件总表。
事件 typeassistant/chunk、tool/result对应 SessionEventMap 的键。
分片 chunk.typetext-delta、tool-call-delta描述流式过程，不是最终消息块。
内容块 content[i].typetext、reasoning、tool-call、tool-result、image描述完整消息的内容组成；不同分支未必都包含 chunk。
其他判别字段role、source.kind、surfaceOp.op、channel分别表示消息角色、来源、Surface 操作与遥测通道。

不是所有字段都逐层嵌套，也没有固定的 JSON 深度。例如工具结果块内部还可以包含内容块；打包存储行有自己的 type: "text-chunks"，但它不是 Session Event。

如果问的是“总共有多少种事件 type”

当前 SessionEventMap 本体声明 13 个核心标签；插件通过 declaration merging 扩展。固定版本生成的 KNOWN_SESSION_EVENT_TYPES 有 44 个已知标签，包含核心 13 个。它表示该版本识别的事件词汇，不代表每个 preset 都会产出这 44 种，也不包含所有传输帧、内容块或存储行标签。

① LLM：先选 Surface，再派生 messages，最后适配厂商协议

事件是否贡献 messages具体规则
user/message是传递内部 UserMessage；用户文本与插件注入的上下文用 source 区分。
assistant/message是，空内容除外完整 AssistantMessage，包含文本、思考或工具调用块；仅承载 usage 的空内容消息跳过。
tool/result是取内部 ToolResultMessage，保留调用关联。
assistant/chunk否保留流式过程，不再重复派生消息。
tool/call否模型的调用块已在 assistant/message 中；执行事件不再生成一份调用消息。
todo/write、Turn / Step 边界否供状态和过程投影；Todo 内容可经工具调用参数与工具结果让模型知道。
request/header不贡献 messages另行记录 system、tools、模型配置，和 messages 一起重建请求。

Surface 不是把日志过滤一次就结束。surfaceOp: "append" 让消息进入尾部；replace 会用新消息遮蔽一段旧 Surface 节点。压缩后，模型可以读摘要，日志仍保留原对话与替换记录。只有 user/message、assistant/message、tool/result 三类事件可进入 Surface。

// 内部工具结果消息：示意，不是完整构造参数。
{ role: "user", content: [{ type: "tool-result", toolCallId: "call-1", content: [...] }] }
                           ↓ DeepSeek serializeMessages
{ role: "tool", tool_call_id: "call-1", content: "文件内容……" }

// 完整请求还包括请求头，messages 只是其中一部分。
{ ...模型配置, messages: deriveMessages(), system: 当前提示词, tools: 当前工具定义 }

内部 Message、Provider WireMessage 与 Event 不是同一种对象。新增模型可见输入，需要留下可重建的事件事实；但“已入日志”不代表“自动进入模型”。

② UI：聊天轨迹与领域状态有两种计算路径

聊天轨迹：客户端归并事件

历史读取 / session/event 帧
  → ConversationEventInput（event + 可选工具展示数据）
  → ConversationNodeAssembler（匹配规则、位置、业务上下文）
  → ConversationViewNode / ViewSnapshot
  → 聊天气泡、工具卡片、执行轨迹

assistant/chunk 持续更新气泡，完整消息到来后形成最终内容；工具调用与结果按 callId 关联成卡片；Turn / Step 边界提供位置与完成状态。因此，一张卡片可以消费多条事件，一条事件也可能影响多个展示结果。

人类聊天历史不能直接复用压缩后的模型 Surface，否则压缩会让用户之前看过的内容消失。原始追加消息是人类历史的材料，替换副本主要服务模型上下文。界面还可能有独立的实时交互状态；不能假设页面上的一切都能由 Session Log 恢复。

领域状态：服务端折叠，客户端接收完整值

ProjectionDefinition = { key, schema, init, apply, view, stateVersion }
  init() → apply(状态, 每条已提交事件) → view(状态)
  → 历史尾页快照 { asOfSeq, values }
  → 实时 session/projection { key, value, seq }
  → 客户端 ProjectionValueStore：较大的 seq 获胜
  → Todo / Plan / Goal / 标题 / 全会话统计

领域注册计算规则，框架统一驱动；与当前领域无关的事件返回同一状态引用，可避免下游更新。客户端不重复实现领域折叠。重启后可以从日志重建，挂载投影缓存时也可从有效缓存接着计算。

投影遵守各领域自己的规则，不是一律“取最后一条”。例如当前 Todo UI 投影在下一次 turn/start 清空；历史 todo/write 仍保留。Plan UI 的 pending 展示也不等于恢复了执行端等待中的 Promise 或切换意图。

③ JSONL：无损编码与持久化，不是内容筛选

SessionHeader → 首行 type: "session"
SessionEvent[] → StorageRecord[] → JSONL 逻辑行 → 可选 Zstd → 文件
                ├─ 原样 SessionEvent
                └─ ChunkRow：text-chunks / reasoning-chunks / tool-call-chunks

读取：文件 → 解压 → 解码存储行 → 连续 seq 的 SessionEvent[] → 重建 Session

默认 packChunks: true、compression: "zstd"。符合条件的至少三条连续同 block delta 可以合并成一个存储行，但成员序号、时间与分片边界都能还原。它没有像遥测那样丢弃中间 chunks。

三个对象要分开：SessionEvent 是逻辑事件，StorageRecord 是存储行值，JSONL / Zstd 是文本与字节编码。打包行不会进入 Session.events，也不是新的领域事件。SQLite 是持久化 seam 的另一个后端，并非必须先写 JSONL 再导入 SQLite。

恢复读取已持久化的前缀，修复中断的工具、Step、Turn 生命周期，再组装可接受新 Turn 的 Agent。只有调用无结果时，不能据此推断外部副作用没发生；恢复后的处理需区分未启动和结果未知。恢复不会复活旧网络流、工具进程或调用栈。

固定 chunk 投影仅保留每个 (turn, step) 的第一条 assistant/chunk，因此 seq 有缺口是正常情况。其他事件在固定投影层透传，之后仍受共享模式与部署方脱敏规则约束。工具错误结果和错误 turn/end 等会映射为 ERROR。

FULL 实时交接，FEEDBACK_ONLY 在反馈事件触发时释放相应日志前缀，DISABLED 不交接。当前默认禁用；脱敏扩展点不自带部署方的脱敏规则，不能把“有扩展点”理解成“已自动清理敏感数据”。

这是 OTel Logs 实现。不能据此认定已有 Traces、Metrics 或账单级投递保证。SDK 队列可能丢失或重复交付，恢复也不保证补发上一进程遗漏的记录。OTel 不参与 agents.resume()，更不能替代权威日志。

统计投影口径 · Header 与来源类型 · 子会话 descriptor

新增功能时可以这样判断：“重启以后必须记住哪件已发生的事？”先给这件事实定义事件和恢复语义，再分别决定模型怎样读、UI 怎样显示、磁盘怎样存、遥测怎样导出。一次文件写入的工具结果可以进入日志，但日志本身不是整个工作区的文件快照。

稳定核验路径：避免只看名字就推断能力

这些是可控的核验方法，不是声称本页已运行真实模型、崩溃注入或外部 Collector 测试。

  1. 固定模型输出：用可控流依次产生文本、工具调用和结果，记录全部事件。对照 deriveMessages，确认 chunks 与 tool/call 没有额外产生重复消息。
  2. 检查两层消息：比较内部 ToolResultMessage 与 DeepSeek serializeMessages 的输出，确认 user + tool-result 转成 wire role=tool。
  3. 触发一次压缩：比较原日志、Surface.nodes 与 UI 历史。原事件仍在，模型输入可被摘要替代，人类历史不能因此被抹去。
  4. 检查持久化往返：同一事件序列分别在 packChunks 开/关时写入；解码后逐字段比较 seq、time、data 与 Surface 元数据。
  5. 检查领域状态：固定 todo/write 后再追加 turn/start，比较 UI 投影和原日志，证明 UI 清单清空不等于删除历史事件。
  6. 检查遥测筛选：同一步发送多条 chunk，验证只导出第一条；再分别测试 FULL、FEEDBACK_ONLY、DISABLED 与脱敏规则。
  7. 检查重启：先 flush 再退出，从耐久日志恢复。查看修复事件与新 Turn，不能把恢复后的消息历史当成旧工具仍在运行的证明。
最常见的五个误判
  • “所有事件都能直接变成模型消息。”——只有指定 Surface 事件派生消息，请求头另走一条路径。
  • “UI 就是 messages 数组。”——UI 还需要分片、边界、工具展示与领域状态。
  • “JSONL 永远是一事件一物理行。”——当前支持无损分片打包与 Zstd。
  • “出现相同 type 字段，就属于同一个类型系统。”——帧、事件、chunk、block、存储行有各自词汇。
  • “OTel 收到数据就能恢复会话。”——遥测是可能经过筛选与脱敏的观测副本。
