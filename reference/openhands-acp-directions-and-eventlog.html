OPENHANDS · AGENT CLIENT PROTOCOL

谁提供 Agent，谁消费 Agent？
OpenHands ACP 的两个方向

在 IDE 里使用 OpenHands，与在 OpenHands 里使用外部 Agent，方向相反。两边都使用 ACP，但事件的生产者、工具的执行者、消息的转换位置和恢复所需的数据各不相同。

先记住两个入口：openhands acp 把 OpenHands 作为 Agent 提供给外部客户端；SDK 的 ACPAgent 则把外部 ACP Agent 接进 OpenHands。ACP 是 Agent Client Protocol，这里讨论的是编码 Agent 与客户端的会话协议。
2 个方向OpenHands 既可以提供 Agent，也可以消费外部 Agent
2 路输出来源完整事件投影 + 可选的实时 token 回调
多对多映射一次事件可产生多条协议消息，也有事件被跳过

同样叫 ACP，OpenHands 站的位置不同

问题方向 A：OpenHands 对外服务方向 B：OpenHands 接入外部 Agent
谁是 ACP Client？IDE 或自己写的 ACP 客户端。OpenHands SDK 里的客户端桥接器。
谁是 ACP Agent / Server？openhands acp 启动的协议进程。Claude Code / Codex / Gemini 等对应的 ACP 子进程。
谁调用模型、执行工具？本页主线为 CLI 的本地 OpenHands Agent 与工作区；CLI 也有 remote 实现。外部 Agent 自己管理模型、工具和执行。
转换发生在哪？CLI 的 EventSubscriber / SharedEventHandler / TokenBasedEventSubscriber。SDK 的 ACPAgent 与 _OpenHandsACPBridge。
记录什么历史？OpenHands 的会话事件；投影后发送给 IDE。外部更新的归并结果进入 OpenHands 事件；外部 Agent 另有自己的历史。
连接方式客户端启动 CLI，以 JSON-RPC over stdio 通信。SDK 启动外部 Agent 子进程，同样以 stdio 通信。

这里的 Server 是协议服务进程。它提供会话、任务提交、输出与执行过程交互；应用的 Web API、模型 API、工具服务和 ACP 是不同接口。

CLI 协议启动入口 · SDK ACPAgent 与客户端桥接

方向 A：外部 IDE 让 OpenHands 完成一次任务

例如在 IDE 中输入：“读取 config.json，解释配置”。IDE 发出 ACP 请求，CLI 把输入转换成 OpenHands 用户消息，驱动 Conversation；产生的事件再经订阅器变成 ACP 更新。

IDE → initialize → 能力协商
IDE → session/new → 创建 Conversation，返回 sessionId
IDE → session/prompt（文本 / 支持的内容块）
        → convert_acp_prompt_to_message_content
        → Message(role="user") → conversation.send_message
        → run_conversation_with_confirmation

Conversation 的事件回调 → EventSubscriber / SharedEventHandler
        → session/update → IDE 更新气泡、思考区、工具卡片、计划

Conversation 运行结束 → 原 session/prompt 请求的响应
        → result: { stopReason: "end_turn" }

回复正文、工具进度与这一轮结束是三个不同信号。session/update 是通知；session/prompt 的 result 是原请求的响应；需要用户批准时还会发出独立的 session/request_permission 请求。

本地 Conversation 配置了 persistence_dir 和事件 callbacks；因此持久化与 ACP 展示消费的是会话事件链路。实时输出通过回调发送，历史恢复则遍历 conversation.state.events，调用转换器。CLI 不会为每条实时更新都先重新扫描磁盘日志。

能力要看实际方法实现：该 CLI 快照的 session/list 返回空列表，session/set_model 是 no-op，session/fork 与 session/resume 不支持；恢复历史使用 session/load 或 CLI 的 --resume 路径。协议中有某个方法名，不等于实现已具备该能力。

Event Log 怎样映射成 ACP 消息？先看非流式事件路径

入口是 EventSubscriber.__call__(event)。它按照事件类分派，SharedEventHandler 再构造具体更新。多数文字来自 event.visualize.plain，工具的结构化输入、输出另放 rawInput / rawOutput。

OpenHands 事件 / 子类型ACP 输出映射细节
普通 ActionEventtool_call，status=in_progresstool_call_id → toolCallId；计算 title、kind、locations；action.model_dump() → rawInput。reasoning 与 thought 非空时先分别发送 agent_thought_chunk。
ThinkActionagent_thought_chunk动作的展示文本进入思考区，不按普通工具卡片起始更新处理。
FinishActionagent_message_chunk将动作的展示文本作为助手输出；它与 prompt result 是不同消息。
普通 ObservationEventtool_call_update，status=completed沿用 toolCallId，展示文本进入 content，event.model_dump() 进入 rawOutput。
UserRejectObservation / AgentErrorEventtool_call_update，status=failed由独立分支识别，填入拒绝或错误展示及原始事件。
TaskTrackerObservationplantask.title → entry.content；todo → pending，in_progress → in_progress，done → completed；priority 固定为 medium。此分支发送计划后直接返回。
ThinkObservation / FinishObservation跳过对应内容已由动作侧表达，结果侧不再生成普通工具完成更新。
MessageEvent：非 user roleagent_message_chunk先取非空的 visualize.plain，再发送助手展示文本。
MessageEvent：user role跳过避免客户端已经显示的用户输入再次出现；该订阅器本身不补发 user_message_chunk。
SystemPromptEvent / PauseEvent / Condensation / CondensationRequestagent_thought_chunk共享处理器把这些事件的展示文本发到思考通道；不能据此把 ACP thoughts 全部当成模型的原始思维内容。
ConversationStateUpdateEvent跳过内部状态管理通知没有对应的 ACP 事件更新。

映射不是固定的一对一。一个 ActionEvent 可以产生 reasoning、thought、tool_call 三条更新；一张工具卡片又依赖动作与结果多条事件。TaskTrackerObservation 有专门的计划分支，不能把它描述成普通完成卡片再自动附加计划。

该快照的普通 Observation 分支直接设置 completed，失败分支显式识别 UserRejectObservation / AgentErrorEvent；不要自行补写“任何 observation.is_error 都自动转成 failed”的规则。方法注释和实现有出入时，本页按执行代码说明。

更新可以附带 _meta["openhands.dev/metrics"]，承载从 conversation stats 读取的 token、cost 和状态行；缺少统计时不附带。这是 OpenHands 扩展元数据，不是把整个事件日志塞进 ACP。

实时 token 路径：不是每条 ACP 更新都来自耐久事件

非流式：完整事件 → EventSubscriber → SharedEventHandler → session/update

开启 --streaming 且满足当前适配条件：
  LLMStreamChunk.delta.content           → agent_message_chunk
  LLMStreamChunk.delta.reasoning_content → agent_thought_chunk
  tool_calls 的名称、ID、参数分片         → tool_call / tool_call_update
  完整 ActionEvent 到来                 → 已开始的卡片只更新摘要与标题
  ObservationEvent 到来                → 结束卡片并清理分片状态

本地 CLI 使用 TokenBasedEventSubscriber.on_token。正文与 reasoning 只取 choice.index=0，工具调用按 tool_call.index 归并；调用 ID、名称及有效参数骨架齐备后才开始显示，think 工具内容走思考区。

完整 ActionEvent 若对应的卡片已在分片阶段开始，订阅器会更新已有卡片，避免再创建一次。流式路径的完整事件处理器不再按普通 MessageEvent 重发整段助手正文；历史重放则使用非流式 EventSubscriber。

当前 CLI 的开关还要求 not agent.llm.uses_responses_api()。因此传入 --streaming 不保证所有模型路径都启用相同 token 回调。

能重放完整历史，不代表能复原每个 token 的原始时序。实时 chunk 可以先显示，再由完整事件沉淀历史；崩溃前尚未形成耐久记录的分片不能靠 ACP 通知本身恢复。这里与 DeepSeek Harness 日志中显式保存 assistant/chunk 的设计要分开看。

分片转换、工具调用归并与完整事件去重 · streaming_enabled 条件与两路回调

权限确认：单独的请求 / 响应，不是“再发一条事件”

ActionEvent 已出现
  → Conversation 进入 WAITING_FOR_CONFIRMATION
  → runner 读取尚未匹配结果的 pending actions
  → ask_user_confirmation_acp
  → session/request_permission（有自己的 JSON-RPC 请求 id）
  → IDE 返回选项
      ├─ 允许：继续；必要时更新确认策略
      ├─ 拒绝：conversation.reject_pending_actions
      └─ 暂缓 / 请求失败：pause，不自动执行

最终 session/prompt 的响应有自己的 id；不会拿权限请求的 id 替代。

CLI 的选项包括一次允许、一次拒绝、持续允许和按风险确认。确认请求使用 confirmation-{sessionId} 作为确认卡片 toolCallId，可以代表一组待执行动作；不要强行把它当成某个原始工具调用的 ID。

取消也走控制面：CLI 的 session/cancel 请求会 pause 会话并等待运行任务停止。历史里出现某个工具卡片或暂停说明，不代表旧进程中的等待对象可在重启后原样复活。

方向 B：外部 ACP 消息怎样进入 OpenHands Event Log？

这个方向使用 SDK 的 ACPAgent。OpenHands 把一个用户回合交给外部 Agent，外部 Agent 决定怎样调用自己的模型与工具；OpenHands 接收协议更新，并转换成自己的展示事件和回合结果。

OpenHands 的用户 MessageEvent
  → _build_acp_prompt：文本 / 支持的图片 + 可选上下文后缀
  → 外部 session/prompt
  → _OpenHandsACPBridge.session_update
      ├─ 文字：累积 + 实时回调
      ├─ 工具：归并 + ACPToolCallEvent
      └─ usage：归集，完成时记录
  → prompt 完成
  → FinishAction + FinishObservation
  → Conversation 回调 → state.append_event → 配置的事件持久化
收到的 ACP 更新当前 SDK 处理OpenHands 事件结果
agent_message_chunk接收文本块，脱敏后累积，向 on_token 发送实时文本。正常完成后合并到 FinishAction.message；不会逐片保存为 MessageEvent。
agent_thought_chunk接收文本块并累积。正常完成后进入最终 ActionEvent 的 reasoning_content。
tool_call缓存 title、kind、status、input、output、content，发出开始记录。ACPToolCallEvent；若首次即终态，则该条也表达终态。
tool_call_update按 toolCallId 归并；中间进度只累计，首次进入终态才发出结果记录。通常每个调用是一条开始 + 一条终态事件，不是每帧一条日志。
usage_update保存 token、上下文窗口等输入；完成时统一记录 usage / cost。走统计处理，不把每条更新复制为普通聊天消息。
plan 等其他更新本快照的该 handler 没有专门转换分支，走调试日志路径。不能认为每一种 ACP SessionUpdate 都有对应的耐久领域事件。

ACPToolCallEvent 是展示事件。它不是 LLMConvertibleEvent，不参与 OpenHands 自己的 LLM messages 转换，也不会让 OpenHands 再执行外部 Agent 已执行过的工具。图上的工具卡片是对外部工作的记录。

正常 prompt 返回时，SDK 会关闭仍未结束的卡片，再生成一对 ActionEvent(FinishAction) / ObservationEvent(FinishObservation)，标记一个完整外部助手回合结束。取消路径会为在途工具发 failed 收尾；这属于桥接层的收尾策略，不能把合成终态理解成额外的远端成功凭据。

OpenHands 这份日志只拥有接收和转换后的事实。外部 Agent 的全部 system prompt、原始模型请求、内部尝试和原生存储，并不会自动完整复制进来。

这个方向的权限处理与 CLI 对外服务不同

固定 SDK 快照的 _OpenHandsACPBridge.request_permission 自动选第一个选项，并返回 AllowedOutcome；不会像方向 A 的 CLI runner 那样向 IDE 发起人工确认。该桥接器还拒绝 elicitation，客户端 fs / terminal 方法不提供实现，外部 Agent 自己执行文件和终端操作。需要人工审批的产品，必须核对或实现自己的交互策略，不能仅凭“支持 ACP”推断已有审批 UI。

{
  "jsonrpc": "2.0",
  "method": "session/update",              // JSON-RPC：这是会话更新通知
  "params": {
    "sessionId": "session-demo",           // 更新属于哪个会话
    "update": {
      "sessionUpdate": "agent_message_chunk", // ACP：这是助手正文分片
      "content": {
        "type": "text",                   // 内容块：文本
        "text": "配置文件包含端口与数据库地址。"
      }
    }
  }
}
// JSONC 示意；真实 JSON 不含中文注释。通知没有 JSON-RPC 请求 id。
标识 / 类型负责什么例子
OpenHands 事件类会话内部发生了什么。ActionEvent、ObservationEvent、ACPToolCallEvent。
ACP Python 模型类构造经过协议模型约束的数据。ToolCallStart、ToolCallProgress、AgentMessageChunk。
JSON-RPC method / id定位方法，匹配请求和响应。session/prompt、session/request_permission；各请求使用自己的 id。
update.sessionUpdate表示本次会话更新种类。tool_call、tool_call_update、plan、agent_message_chunk。
content.type表示协议内容块的格式。text 等；与事件类、方法名不是同一份枚举。
sessionId / toolCallId / event.id分别关联会话、工具生命周期和具体事件。同一个 toolCallId 可出现在多条事件和多次更新里；不能拿它当所有消息的唯一 ID。

Python 里的 tool_call_id、raw_input 等字段序列化到 ACP wire 时对应 toolCallId、rawInput。UI 端拿到的是协议读模型，不能直接按 OpenHands 原始事件类去解释每条通知。

恢复：历史展示和外部 Agent 续聊各需要什么？

场景现有路径不能推导出的保证
方向 A：重新显示 OpenHands 历史session/load 读取 Conversation；遍历 state.events，用新的 EventSubscriber 逐条投影。--resume 的相应路径也重放历史。不是原始 token 时序的无损回放；该 subscriber 跳过 user role 消息，完整用户历史展示还需核对客户端整合。
方向 A：等待确认时中断恢复持久会话状态后，runner 可处理 WAITING_FOR_CONFIRMATION 并重新发起确认。原 JSON-RPC 请求、旧连接和 Promise 不会原地复活；具体恢复条件依赖实际保存的状态。
方向 B：显示已有外部工具轨迹读取 OpenHands 保存的 ACPToolCallEvent 与最终 Finish 事件。展示恢复不代表外部 Agent 的原生模型上下文已恢复。
方向 B：让外部 Agent 继续记得前文SDK 持有 / 读取原生 ACP session ID，并在对方支持时调用 load_session；还需要对方自己的历史数据仍存在。只有 OpenHands Event Log 不足以恢复外部 Agent 全部内部状态；load 失败可退回新会话。

ACP 消息投影、模型上下文、持久化、观测是不同消费者。对比前一篇：可以在同一条事件链上派生多个结果，但每条协议消息是否进入耐久日志，必须查实际生产和保存路径。

稳定核验路径：不依赖模型临场决定是否调用工具

下面是建议的可控核验步骤。本次页面制作核对了固定源码，并检查静态页面与说明器；未运行 OpenHands 真实模型、外部 Agent 或恢复集成测试。

  1. 对外服务：固定普通 ActionEvent / ObservationEvent，收集 session_update 调用；验证相同 toolCallId 的开始与 completed 更新，并核对 rawInput / rawOutput。
  2. 特殊动作：分别输入 ThinkAction、FinishAction、TaskTrackerObservation，检查 thought / message / plan 分支；用 UserRejectObservation 检查 failed。
  3. 跳过与一对多：输入用户 MessageEvent、ConversationStateUpdateEvent，确认没有对应更新；给一个动作同时设置 reasoning 和 thought，观察它产生多条通知。
  4. 流式去重：先输入工具调用分片，再输入同 ID 的完整 ActionEvent；确认更新已有卡片而非再次开始。与非流式历史重放结果分别比较。
  5. 权限确认：mock 客户端的 permission 响应，覆盖允许、拒绝和调用异常；检查 runner 的继续、reject_pending_actions 与 pause。方向 B 单独验证其自动选项行为。
  6. 反向入库：给 SDK bridge 发送工具 start、多条 in_progress、一次 completed；核对日志通常只有开始与首次终态，且 ACPToolCallEvent 不触发 OpenHands 工具执行或 LLM 消息转换。
  7. 结束与恢复：正常完成后核对 FinishAction / FinishObservation；分别保留、移走外部 Agent 原生历史，验证“能显示旧卡片”和“外部 Agent 仍记得前文”是两个检查。
用一句话回答最容易问混的问题
ACP 对外提供什么？
提供可被 IDE 或程序驱动的编码 Agent 会话服务：接任务、持续反馈执行信息、处理控制与确认。
OpenHands UI 直接消费 ACP 吗？
在方向 B 的结构中，ACP 终止于 SDK bridge；它再把可展示的事件交给 OpenHands 会话与上层 UI。
Event Log 与 ACP 是同一种格式吗？
各自有类型和用途。转换器可以拆分、归并、格式化、跳过；token 回调还可以独立产生更新。
可否把方向 A 和 B 串起来就认为完全等价？
不能自动这样推断。CLI subscriber 的分派没有 ACPToolCallEvent 专门分支，SDK bridge 也没有把所有 SessionUpdate 都保存；需要明确适配和验证。
本页的“思考”都来自模型 reasoning 吗？
不是。CLI 也把系统提示、暂停与压缩事件的展示文本映射到 agent_thought_chunk。
