Plan：日志、UI、恢复与 LLM 消息

分别说明计划模式、方案正文、任务清单和用户批准如何保存、显示、恢复，以及进入模型上下文。

Plan 关心方案和决定：当前是否处于规划模式、方案正文是什么、任务清单怎样更新、用户是否批准。保存方案不等于保存执行位置。

先把 Plan 拆成三件事

对象例子恢复时问什么
计划模式现在只探索和设计，暂不进入执行。重启后策略、工具配置和模式状态能否恢复？
计划正文 / Todo先查接口，再改前端，最后验证。正文、任务清单保存在哪里？是否重新进入模型上下文？
计划批准用户点击“批准并执行”。批准决定是否落盘？等待中的交互是否还能回答？

Todo 是进度清单，不自动产生依赖边、失败重试和工作流 checkpoint。Plan mode 也不天然等于只读沙箱；实际约束要看工具和权限实现。

核对日期：2026-10-09。DeepSeek 使用本仓库固定源码；另外两家的一手源码链接到 main，版本变化后需要重新核对。事件示例省略时间、序号等字段，不是实际运行记录。

Plan ① DeepSeek：模式、正文与批准各走不同路径

模式状态的日志与 UI

/plan → command/run（记录用户选择）
      → 无 open turn：立即写 plan/mode {active:true}
      → 有 open turn：在下一个被接受的 pre-step 写 plan/mode

UI plan 投影：command/run 记录 wanted；plan/mode 更新 active 并清 wanted
              → {active, pending} → 输入区 Plan 状态按钮

LLM：读取当前模式 → 激活 plan:policy system prompt 段落

plan/mode 最新值决定已提交模式，默认 inactive。UI 还折叠 command/run 来展示待应用选择。投影能重建 pending 展示，不等于执行端 pendingIntents 已恢复。运行中选择尚未到接受边界，或模型批准后的退出尚未写 plan/mode 时，进程退出可能丢失执行端待切换意图，需要重申选择。

裸 /plan、/plan off 及其命令结果不进入普通消息历史。/plan 的任务后缀作为 user 文本进入消息；模式控制通过 system prompt 生效。某些用户主动切换会额外记录模型可读通知，不能因此将所有 plan/mode 事件都转换成用户消息。模式改变影响请求前缀，不只是聊天尾部追加。

正文与用户批准的日志、UI 和 LLM

方案正文保存在 assistant 工具调用参数及 tool/call 中，历史工具卡片通过 presentCall 展示；不是 plan/mode 中保存了整份计划。成功工具 API 值为 {approved:true}，模型可读结果由 render 生成“计划批准并退出”的确认文本，不能把 API 值与最终 LLM 内容混为一谈。拒绝反馈由错误工具结果进入模型。

已批准并提交模式切换后，历史工具调用/结果和模式状态可恢复。刷新但主机活着时，评审请求由 pendingQuestions 重发；崩溃后待批准 Promise 不会从日志复活，按 QA 中断修复规则处理。计划模式是提示策略，独立沙箱/权限才负责强制限制。

plan/mode、投影、exit_plan_mode 与边界提交 · 模型体验和恢复限制 · 模式 UI · 计划评审 UI · 评审通道的 QA 恢复细节

Todo 是另一份计划数据

todo_write 整体替换任务清单并追加 todo/write。该事件是 UI/重放快照，不另产生 LLM 消息；模型通过自身工具调用参数知道完整清单，通过工具结果知道更新摘要。当前 UI todos 投影在下一次 turn/start 清空：持久历史还在，不代表新一轮仍显示旧清单。

Plan ② Deep Agents：显式启用 Todo；批准另外建模

版本提醒：Python Deep Agents 0.7.0 起，create_deep_agent 不再默认加入 TodoListMiddleware、write_todos 和 todos 状态。需要通过 middleware 显式添加；旧资料里的“默认内置”不适用于这个版本。
AIMessage.tool_calls：write_todos（完整列表）
                     ↓ 工具返回 Command
state.todos          ← 最新列表（checkpoint 保存，供 UI 读取）
state.messages       ← ToolMessage（更新内容，关联工具调用 ID）
                     ↓
UI：订阅 todos state 并显示；恢复时读取 checkpoint
LLM：AIMessage 调用 + ToolMessage；不是自动把全部 state 字段变成消息

TodoListMiddleware 的工具同时更新 todos 和 messages 两条状态通道。它还提供工具使用 system prompt。清单内容可以通过工具消息进入模型；todos 状态供 UI 使用，但没有自动完成任务、自动恢复外部副作用的保证。

方案正文若存文件，恢复依赖所选 backend；若存自定义 plan 字段，则依赖图 state/checkpointer，并由模型节点显式读取。需要“提交方案 → 用户批准”时，可以另建 interrupt 节点或应用层 ask_user 交互，将批准决定写入状态和消息。这是应用组合方案，不能宣称 TodoListMiddleware 自带 DeepSeek 的 plan/mode 或 exit_plan_mode 协议。

持久化 checkpoint 可以恢复清单和等待点；只有内存 saver 不提供跨进程恢复。重载历史 ToolMessage 可以重建已完成的工具行；重新显示未批准交互还需要 pending interrupt。

Plan ③ OpenHands：PLAN.md 和任务清单分别保存

方案正文：Planning preset + 文件

Planning Agent：planning prompt + Glob / Grep / PlanningFileEditor
              ↓ 工具 ActionEvent
执行器读写 PLAN.md（默认 .agents_tmp/PLAN.md，兼容根目录旧文件）
              ↓ ObservationEvent（内容 / 修改结果）
EventLog → UI 工具卡片；View → LLM 工具调用和结果

完整方案：工作区文件；日志：某次操作和结果，不天然等于文件快照。

PlanningFileEditor 可以读其他文件，但编辑被限制到计划文件。方案标题和章节由 planning preset 提示规定；这比纯提示限制更具体，但不代表所有自定义 planning Agent 都有相同约束。

重载 EventLog 能恢复操作历史；完整 PLAN.md 的恢复还依赖工作区文件保留。模型可以通过此前的编辑/读取结果知道方案，或重新读取文件；文件存在不代表它会自动完整注入后续每次 LLM 请求。UI 可显示工具结果或通过应用层文件面板显示正文，SDK 不保证统一的“批准计划”卡片。

Planning preset · 计划路径、初始化与工具定义 · 限制编辑文件的执行器

任务清单：TaskTracker + 独立文件

task_tracker 的 plan 命令更新列表，view 命令读取列表；ActionEvent/ObservationEvent 进入 EventLog，Observation 的 task_list 可用于 UI。执行器以 persistence_dir 作为 save_dir 时，实际通过 TASKS.json 保存/恢复任务列表（不是只靠 EventLog，源码部分说明文字提到 TASKS.md，但实际读写路径为 JSON）。保存失败会告警，工具成功不能独自证明该文件已落盘。

plan 的结果 content 通常是更新数量摘要；view 的结果 content 才格式化完整清单。ActionEvent 通过 tool_call 生成 assistant 工具调用；ObservationEvent 通过 observation.to_llm_content 加 extended_content 生成 role=tool 消息。TaskTrackerObservation 沿用默认 to_llm_content，读取 content（错误时附加错误头），不会额外序列化 task_list。配置了持久化目录可以恢复清单；任务状态并不恢复业务步骤执行位置。

用户对方案的文字确认可以作为 User MessageEvent 保存；若需要结构化批准及持久等待点，应用层还需定义状态和恢复协议。执行批准和方案批准是不同业务决定。

稳定核验路径

以下是建议验证流程；本次核对源码并检查静态站点，没有运行三家真实模型会话。使用固定工具调用或可控适配器触发，避免依赖模型是否主动调用工具。

  1. 计划模式：在 idle 和 open turn 分别切换 /plan，检查 command/run、plan/mode 与 system prompt。边界前重启，区分 UI pending 和执行端待切换意图。
  2. 方案与批准：固定正文，分别批准、拒绝、关闭和评审时重启；检查工具结果、反馈及模式切换的先后关系。
  3. Todo：检查清单快照或 todos checkpoint，并核对工具调用/结果。DeepSeek 下一轮清空 UI 投影不等于删除历史清单。
  4. 文件恢复：分别保留和移走 OpenHands PLAN.md、TASKS.json，证明操作日志、方案文件和当前任务状态不是同一份存储。
  5. 模型上下文：核对模式提示、正文参数、批准反馈、Todo 结果或文件读取内容，避免把结构化 UI 字段误认成模型消息。
