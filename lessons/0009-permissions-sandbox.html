第 9 课：Permission、Approval 与 Sandbox

策略决定默认权限，审批允许单次严格升级，内核沙箱负责真正执行限制，Session 事件负责审计与恢复。

本课导览

包含内容权限模式、审批策略、单次授权、审计事件、平台沙箱和恢复。
涉及模块PermissionService、审批响应器、工具效果声明、LocalSandbox、Session 权限投影。
白话解释策略先决定默认能做什么；确实需要更多权限时询问用户；操作系统沙箱负责最后一道硬限制。
解决的问题避免模型自行扩大权限，让每次高风险操作都有最小授权、可执行限制和可恢复审计记录。

完整能力清单

能力具体覆盖安全不变量
沙箱模式只读、工作区写入和完全访问三级权限，支持严格单向升级。请求权限不得低于工具实际效果。
审批策略支持询问与从不询问；审批结果包含单次允许、拒绝、取消和不可用。单次允许不污染后续调用。
审批交互携带工具、参数、理由、当前模式和请求模式，响应器可异步回答。没有响应器时确定性拒绝。
取消竞态审批等待可取消，迟到回答被丢弃。一次询问最多产生一个决定。
审计事件询问、决定、模式和策略写入 Session，并可投影待处理审批。拒绝没有对应询问的孤立决定。
状态恢复从最后的权限模式和审批策略事件恢复服务状态。进程重启不重置会话权限语义。
内核沙箱macOS 上以平台沙箱执行真实进程，工作区写入仅开放指定目录。策略判断和操作系统强制限制必须同时成立。

主概念深挖：授权决策与强制执行

权限系统的上游是工具意图和会话策略，下游是本地执行层；Session 提供可恢复策略，审批提供用户决策，操作系统沙箱负责不可绕过的最终执行。

ToolEffect + arguments（输入）
            │
            ▼
PermissionService ── policy ──► allow / reject
            │ 需要升级
            ▼
InteractionBroker / 用户审批
            │ allowed-once
            ▼
LocalSandbox ─► Process / FS（下游执行）
            │
            └── ask/decision/mode events（审计输出）
背景与目的模型不能成为自己权限的裁判；同时只靠用户弹窗也无法阻止已经获准的进程越界访问。
输入与输出输入是工具效果、当前模式、请求模式、理由、策略和取消信号；输出是允许或拒绝决定、审计事件及沙箱执行配置。
适用场景只读审查、工作区文件修改、安装依赖、访问工作区外资源和无人值守运行。
底层组件三级权限偏序、审批响应器、一次性决定、Session 审计投影、macOS sandbox-exec 规则。
核心逻辑先计算工具最低权限，验证请求是严格升级；策略允许询问时记录 ask，首个有效回答写 decision；执行阶段再由 OS 沙箱限制实际系统调用。
权衡细粒度审批提升安全与可审计性，但增加交互摩擦；单次授权避免永久放宽，又可能要求重复确认。
方案对比仅提示用户属于软约束，工具可绕过；仅沙箱缺少业务意图与审计；两者叠加才能同时回答“应不应该”和“能不能”。

严格升级规则

read-only → workspace-write → danger-full-access

sandbox_permissions 与 justification 必须同时出现；
目标必须严格宽于当前模式；
目标还必须满足工具声明的 minimumMode；
approval/policy=never 时不调用任何 answerer；
没有 answerer 时 fail closed。
策略检查不是沙箱。如果只在 TypeScript 里判断后直接启动 bash，恶意或误判命令仍可能越界。本课在 macOS 下实际用 sandbox-exec/Seatbelt 包装 argv；没有可用受限 runner 的平台必须返回 SANDBOX_UNAVAILABLE，不能静默裸跑。

恢复规则

恢复不读取 OTel Logs，也不保存内存里的“已批准”布尔值。长期策略由 Session Event 最后写入获胜；一次性批准只证明历史上的那个 call 为什么执行，不能在恢复后复用。
