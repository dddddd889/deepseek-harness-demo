完整能力清单

能力具体覆盖安全不变量
沙箱模式只读、工作区写入和完全访问三级权限，支持严格单向升级。请求权限不得低于工具实际效果。
审批策略支持询问与从不询问；审批结果包含单次允许、拒绝、取消和不可用。单次允许不污染后续调用。

审计事件询问、决定、模式和策略写入 Session，并可投影待处理审批。拒绝没有对应询问的孤立决定。
状态恢复从最后的权限模式和审批策略事件恢复服务状态。进程重启不重置会话权限语义。
内核沙箱macOS 上以平台沙箱执行真实进程，工作区写入仅开放指定目录。策略判断和操作系统强制限制必须同时成立。

主概念深挖：授权决策与强制执行

权限系统的上游是工具意图和会话策略，下游是本地执行层；Session 提供可恢复策略，审批提供用户决策，操作系统沙箱负责不可绕过的最终执行。

ToolEffect + arguments（输入）
            │
            ▼

            │ 需要升级
            ▼
InteractionBroker / 用户审批
            │ allowed-once
            ▼
LocalSandbox ─► Process / FS（下游执行）
            │
            └── ask/decision/mode events（审计输出）
背景与目的模型不能成为自己权限的裁判；同时只靠用户弹窗也无法阻止已经获准的进程越界访问。
输入与输出输入是工具效果、当前模式、请求模式、理由、策略和取消信号；输出是允许或拒绝决定、审计事件及沙箱执行配置。
适用场景只读审查、工作区文件修改、安装依赖、访问工作区外资源和无人值守运行。
底层组件三级权限偏序、审批响应器、一次性决定、Session 审计投影、macOS sandbox-exec 规则。
核心逻辑先计算工具最低权限，验证请求是严格升级；策略允许询问时记录 ask，首个有效回答写 decision；执行阶段再由 OS 沙箱限制实际系统调用。
权衡细粒度审批提升安全与可审计性，但增加交互摩擦；单次授权避免永久放宽，又可能要求重复确认。
方案对比仅提示用户属于软约束，工具可绕过；仅沙箱缺少业务意图与审计；两者叠加才能同时回答“应不应该”和“能不能”。

场景穷举

工具请求
├─ 最低权限 ≤ 当前模式 → 直接执行
├─ 严格升级 + ask → 记录询问 → 单次允许/拒绝/取消
├─ 严格升级 + never → 不询问，直接拒绝
├─ 缺少回答器 → APPROVAL_UNAVAILABLE
├─ 非严格或参数不成对 → 提问前拒绝
└─ 已允许 → OS 沙箱仍限制真实访问
场景策略结果执行结果
只读工具当前只读模式足够。直接运行，但仍受文件边界限制。
工作区写入用户单次允许升级。仅本次在 workspace-write 沙箱运行。
越界写入即使业务层错误批准。强沙箱仍拒绝工作区外写入。
审批取消竞态等待者先取消。迟到允许无效，只写 cancelled 决定。
冷恢复读取最后模式和策略事件。恢复后继续相同授权语义，不恢复一次性许可。

关键设计反问

模型传入 requestedMode 是否等于获得权限？
不等于。它只是请求材料，权限服务必须结合工具最低效果、当前模式、策略和用户决定独立判定。
为什么单次允许不写成新的会话模式？
一次性许可只针对当前工具参数；提升会话模式会让之后所有调用意外继承更高权限。
平台没有强沙箱时怎么办？
必须在能力探测中明确标记，仅进程隔离不能冒充强沙箱；高风险场景应拒绝而非静默降级。

沙箱模式：三框架分别怎么做？

同一个问题：选择只读后，究竟限制了什么操作？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
bash-sandbox 将 read-only、workspace-write 映射为文件影响约束；danger-full-access 直接绕过 runner。网络和进程可见性不在这些模式的承诺内。 依据 permissions 按路径和读写操作约束内置文件工具，不覆盖自定义/MCP 工具或任意 execute；不能把一条只读规则当作整个进程只读。 依据 Workspace 选择本地、Docker 或远程执行环境；文件和进程隔离取决于该环境的部署，不能由一个动作确认开关代替。 依据

这个概念的区别：先问约束对象是文件工具、shell 文件影响还是整个执行环境，再比较“只读”。

内核沙箱：三框架分别怎么做？

同一个问题：业务层错误放行后，哪一层还能阻止越界？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
Linux 选择 bwrap 或 Landlock，macOS 用 Seatbelt，Windows 用受限令牌；runner 不可用则失败关闭。Windows 与旧 Landlock ABI 可能仅部分强制执行。 依据 LocalShellBackend 在宿主执行，路径虚拟化不能约束 shell；需要强隔离时应选择 sandbox backend，而不是只配置 root_dir。 依据 DockerWorkspace 以容器提供执行环境；LocalWorkspace 直接使用宿主进程。RemoteAPIWorkspace 只是连接远程服务，仍需核对服务实际隔离配置。 依据

这个概念的区别：审批回答“是否允许”，隔离回答“最多能做什么”；操作系统限制的覆盖面和降级情况必须单独列明。

严格升级规则

read-only → workspace-write → danger-full-access

sandbox_permissions 与 justification 必须同时出现；
目标必须严格宽于当前模式；
目标还必须满足工具声明的 minimumMode；
approval/policy=never 时不调用任何 answerer；
没有 answerer 时 fail closed。
策略检查不是沙箱。如果只在 TypeScript 里判断后直接启动 bash，恶意或误判命令仍可能越界。本课在 macOS 下实际用 sandbox-exec/Seatbelt 包装 argv；没有可用受限 runner 的平台必须返回 SANDBOX_UNAVAILABLE，不能静默裸跑。

审批策略：三框架分别怎么做？

同一个问题：关闭审批提示，是自动拒绝还是直接执行？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
ask 尝试应答者，缺失或失败则拒绝；never 在交互分发前拒绝需要审批的请求。allowed-once 只授权所请求操作。 依据 文件权限规则按首条匹配决定 allow、deny 或 interrupt，未匹配则允许；规则顺序会改变结果。 依据 AlwaysConfirm 要求确认，NeverConfirm 不要求确认，ConfirmRisky 按风险阈值决定是否询问。 依据

这个概念的区别：DeepSeek 的 never 与 OpenHands 的 NeverConfirm 含义相反：前者不许询问并拒绝需审批操作，后者跳过确认。

审批交互：三框架分别怎么做？

同一个问题：用户看到什么，批准后如何继续？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
approval/request waterfall 找应答者，结果为允许一次、拒绝、取消或不可用；原 seam 带工具名、理由和可选调用 id，不携带工具参数，区别于本课教学请求结构。 依据 interrupt 暴露可序列化载荷；应用用原 thread_id 和 Command(resume=...) 回传决定并继续图执行。 依据 Conversation 在待确认动作上暂停，由用户批准或拒绝后继续；安全分析器负责评估，确认策略决定是否需要交互。 依据

这个概念的区别：对比审批界面前，先核对请求载荷和恢复入口；教学示例里能展示参数，不代表上游审批 seam 自带参数。

取消竞态：三框架分别怎么做？

同一个问题：等待批准时取消，还能接受迟到的允许吗？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
请求绑定尚未结束的轮次；中止解析为 cancelled，决定必须先提交审计才能返回，不能产生未记录的授权。 依据 interrupt 是可持久暂停，不是进程取消；恢复需要匹配 thread/interrupt，节点从头重跑。应用若允许撤销审批，应另外校验请求仍有效，而非把迟到回复直接用于新运行。 依据 确认机制针对待执行动作；不能据此推导运行中工具已终止。审批取消与执行终止应分别验证，本次引用未给出与 DeepSeek 一次性请求相同的竞态保证。 依据

这个概念的区别：比较三个时刻：批准前取消、批准后未执行、工具已开始。暂停等待与杀掉进程不是同一个保证。

恢复规则

恢复不读取 OTel Logs，也不保存内存里的“已批准”布尔值。长期策略由 Session Event 最后写入获胜；一次性批准只证明历史上的那个 call 为什么执行，不能在恢复后复用。

审计事件：三框架分别怎么做？

同一个问题：审批记录会直接成为模型上下文吗？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
approval/asked 与 approval/decided 成对写 Session，但只写日志；模型看发起方最终工具结果，不重复消费人类审批界面。 依据 interrupt 载荷随暂停暴露并由检查点保留执行位置；业务需要独立审计记录时，应显式设计状态/存储，不能假设有 asked/decided 同名事件。 依据 Conversation 的事件记录与状态持久化分开；确认状态不能简单映射成 DeepSeek 的审计对，模型可见事件也应按事件转换规则判断。 依据

这个概念的区别：“能恢复审批”等于保存了控制状态，不自动等于完整业务审计，更不等于要把审计内容全部发给模型。

状态恢复：三框架分别怎么做？

同一个问题：重启后沿用旧权限，还是采用新的默认配置？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
permission-presets 为新会话固定预设、模式和策略；恢复 seed 保留有效权限，只补缺失事实，不采用最新用户默认值。一次性允许不是永久授权。 依据 恢复 interrupt 依赖持久 checkpointer 和相同 thread_id；这保存图状态，但应用重新装配的权限规则是否变化仍须自行控制。 依据 同一 conversation id 与持久化目录用于恢复状态和事件；这不意味着容器/主机的当前权限也被回滚，执行环境仍是独立边界。 依据

这个概念的区别：分别验证会话策略、未决审批和执行环境；不要用“会话恢复成功”替代权限一致性检查。
