主概念深挖：工具执行管线

工具管线位于模型工具调用的下游、真实业务函数和权限系统的上游，是不可信模型输出进入外部世界前的验证与调度边界。

模型 tool-call(name, raw JSON, callId)
                  │ 输入
                  ▼
Registry.prepare ─► Schema 校验 ─► Permission
                                      │ allow
                                      ▼
                              Scheduler ─► Tool body
                                      │
                                      ▼
                         ToolOutcome / ToolResult（输出）
                                      │
                                      ▼
                               Session ─► 下一 Step
背景与目的模型产生的是概率性文本，不能直接当成可信函数参数；执行前必须确认名称、结构、权限和并发属性。
输入与输出输入是工具名、调用标识和原始 JSON；输出是与调用标识关联的成功或失败工具结果消息。
适用场景文件操作、终端命令、搜索、MCP 工具、多个独立查询并行执行。
底层组件工具注册表、JSON Schema 子集校验器、PreparedCall、权限效果、批次调度器和结果规范化器。
核心逻辑先解析校验全部调用，再按并行安全性分组；执行结果无论返回还是抛错都规范化，最后严格按模型顺序提交到 Session。
权衡严格模式会拒绝部分可自动修正参数，但避免工具主体承担模糊输入和隐式安全决策。
方案对比让每个工具自行校验自由度高却重复且不一致；统一管线集中策略，代价是要维护一套公共模式能力。

场景穷举

工具调用批次
├─ 全部安全并行 → 同时执行，按模型顺序提交
├─ safe, exclusive, safe → 两侧并行组被屏障隔开
├─ JSON/Schema 错 → body 不执行，返回校验结果
├─ 工具抛错 → 规范化 ToolError
├─ 权限拒绝 → 规范化权限结果
└─ cancel → 等待协作结束，写取消结果
场景调度结果语义
单个只读工具直接执行。成功值投影为工具消息。
多个独立查询并行重叠执行。提交顺序仍等于模型调用顺序。
写工具夹在中间形成前后屏障。避免读写次序被并发打乱。
坏参数准备阶段停止。错误携带参数路径，工具 body 零调用。
未知执行结果进程崩溃后不在本层自动重试。由恢复层记录 TOOL_OUTCOME_UNKNOWN。

多方案对比

方案吞吐顺序保证复杂度
全部串行低。最强。最低，适合工具很少。
全部 Promise.all高。弱，副作用易乱序。表面低、故障成本高。
安全并行+独占屏障中高。显式可控。需工具声明并行安全性。
事务调度器取决于冲突检测。可提供更强原子性。要求工具支持事务或补偿。

关键设计反问

并行安全性为什么由工具声明？
调度器看不到函数内部副作用，只能由工具作者提供最小事实；默认值应保守为不可并行。
为什么结果按模型顺序提交而不是完成顺序？
模型下一步按调用顺序关联 callId；完成顺序会让重放随机器时序漂移。
工具异常应该让 Agent 崩溃吗？
通常不应。工具失败是模型可以观察并修正的业务结果；只有框架不变量损坏才应升级为基础设施错误。

并发调度

parallel A ─┐
parallel B ─┴─ 同时执行 ── 按 A、B 顺序提交结果
exclusive C ─ 单独执行，形成屏障
parallel D ─ 下一并发组
执行顺序不等于提交顺序。安全工具的 body 可以重叠，但 Session seq、tool/result 和下一模型上下文必须保持模型原始 call 顺序。
