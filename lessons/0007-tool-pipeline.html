第 7 课：工具管线与多 Step Agent

模型只产生原始 tool-call；Registry 才拥有 schema 和函数。工具结果落账后，Agent 使用同一 Session 投影发起下一 step。

本课导览

包含内容工具注册、参数校验、调用准备、并发调度、结果规范化和多步骤循环。
涉及模块ToolRegistry、JSON Schema 校验器、工具调度器、HarnessAgent。
白话解释模型只填写“想调用什么和传什么参数”，真正能不能执行、怎么执行由工具管线把关。
解决的问题阻止坏参数和未知工具进入业务函数，统一异常结果，并安全地支持并行工具与连续模型步骤。

完整能力清单

能力具体覆盖失败语义
工具注册保存模型可见模式与执行函数，列出稳定工具定义。未知工具返回关联调用标识的工具结果。
参数准备解析原始 JSON，并校验类型、必填字段、枚举、数组、对象和额外字段。执行函数在校验通过前绝不运行。
结果规范化成功值、业务失败和抛出异常统一转成结构化工具结果消息。错误码、名称和消息可重放。
并行调度相邻安全调用可重叠执行，独占工具在前后并行组之间形成屏障。提交顺序始终遵循模型调用顺序。
权限接缝执行前读取工具效果，交给权限服务决定是否允许或升级。工具主体不自行绕过审批。
多步骤回路结果落账后重新投影消息并调用下一模型步骤。最大步骤数阻止无限工具循环。
取消收尾取消信号传入工具并等待协作式结束。写入取消结果后再闭合步骤与轮次。

主概念深挖：工具执行管线

工具管线位于模型工具调用的下游、真实业务函数和权限系统的上游，是不可信模型输出进入外部世界前的验证与调度边界。

模型 tool-call(name, raw JSON, callId)
                  │ 输入
                  ▼
Registry.prepare ─► Schema 校验 ─► Permission
                                      │ allow
                                      ▼
                              Scheduler ─► Tool body
                                      │
                                      ▼
                         ToolOutcome / ToolResult（输出）
                                      │
                                      ▼
                               Session ─► 下一 Step
背景与目的模型产生的是概率性文本，不能直接当成可信函数参数；执行前必须确认名称、结构、权限和并发属性。
输入与输出输入是工具名、调用标识和原始 JSON；输出是与调用标识关联的成功或失败工具结果消息。
适用场景文件操作、终端命令、搜索、MCP 工具、多个独立查询并行执行。
底层组件工具注册表、JSON Schema 子集校验器、PreparedCall、权限效果、批次调度器和结果规范化器。
核心逻辑先解析校验全部调用，再按并行安全性分组；执行结果无论返回还是抛错都规范化，最后严格按模型顺序提交到 Session。
权衡严格模式会拒绝部分可自动修正参数，但避免工具主体承担模糊输入和隐式安全决策。
方案对比让每个工具自行校验自由度高却重复且不一致；统一管线集中策略，代价是要维护一套公共模式能力。

完整工具回路

step 1 / assistant message
          │ tool-call(name, raw JSON, callId)
          ▼
ToolRegistry.prepare
  ├── 查找工具
  ├── JSON.parse（失败保留原文）
  ├── JSON Schema 校验
  └── 决定 parallel / exclusive
          │
          ▼
append tool/call ──> execute ──> normalize ──> append tool/result
                                                        │
                                                        ▼
                                              step 2 / model request
失败点稳定 code是否进入下一 step
名字未注册UNKNOWN_TOOL是，让模型看到错误并修正
坏 JSON/schema 不匹配INVALID_ARGUMENTS是
execute 抛异常TOOL_EXECUTION_FAILED是
协作式取消TOOL_ABORTED否，闭合当前 turn
无限工具循环MAX_STEPS否

并发调度

parallel A ─┐
parallel B ─┴─ 同时执行 ── 按 A、B 顺序提交结果
exclusive C ─ 单独执行，形成屏障
parallel D ─ 下一并发组
执行顺序不等于提交顺序。安全工具的 body 可以重叠，但 Session seq、tool/result 和下一模型上下文必须保持模型原始 call 顺序。
