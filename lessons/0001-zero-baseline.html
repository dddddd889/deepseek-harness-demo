主概念深挖：可调试基线

可调试基线位于所有 Harness 能力的最上游：上游输入是源码、配置和工具链，下游是后续 16 课的所有运行能力；它不提供业务功能，却决定后面每次失败能否被可靠复现和定位。

源码与配置（输入）
      │ Bun 加载 + TypeScript 检查
      ▼
可运行程序 ──► bun:test 验证 ──► VS Code 断点观察
      │                         │
      └──────── 退出码、日志、调用栈（输出）
背景与目的复杂系统里“环境坏了”和“代码坏了”症状相似；先建立可重复的运行、类型、测试和断点链路，后续调试才有可信起点。
输入与输出输入是源码、编译配置、依赖和测试；输出是程序结果、类型诊断、测试报告、退出码及断点状态。
适用场景首次搭建仓库、升级 Bun 或 TypeScript、迁移机器、CI 与本地结果不一致时。
底层组件Bun 运行时与测试器、TypeScript 编译器、源码映射、VS Code 调试适配器。
核心逻辑先运行最小入口，再制造一个确定失败的断言，最后在同一源码上命中断点；三条证据共同排除“假绿”和映射错误。
权衡基线阶段刻意不接模型和插件，牺牲功能演示速度，换取问题空间最小和后续回归可信。
方案对比直接运行完整应用反馈丰富但变量太多；最小垂直基线信息少，却能最快区分工具链故障与业务故障。

场景穷举

开始验证
├─ 运行成功、测试通过、断点命中 → 基线成立
├─ 运行失败、类型检查失败 → 先修工具链或源码
├─ 测试永远通过 → 反向制造失败，排查假测试
├─ 断点不命中 → 检查启动目标与源码映射
└─ 本地通过、CI 失败 → 对齐版本、环境和工作目录
场景观察处理
正常入口、类型检查、测试和断点四条链路全部成功。冻结版本与命令，作为后续课程共同入口。
边界空输入、最小文件或无依赖时仍能启动和退出。保留最小夹具，避免把业务数据当作工具链前提。
失败编译错误、断言错误或非零退出能被明确报告。确认失败发生在哪一层，不用后续模块掩盖根因。
恢复重装依赖或换机器后结果漂移。按锁文件、运行时版本、配置、工作目录顺序恢复。
误用只运行一次 Hello 就宣称环境可靠。必须反向证明测试能失败、断点能观察真实源码。

关键设计反问

为什么“测试通过”还不够？
测试可能根本没有运行目标代码，或断言永远为真；必须故意制造失败证明测试链路有辨别力。
为什么第一课就需要断点？
后续大量问题涉及事件顺序和竞态，只看最终输出无法判断中间状态；调试能力必须先于复杂状态机。
能否直接用系统全局 Bun？
可以，但必须固定并打印版本；否则机器或 CI 升级后出现的行为变化无法和代码变化区分。

调试基线：三框架分别怎么做？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
