主概念深挖：模型流式适配层

流式适配层位于外部模型 API 的下游、Agent 模型步骤的上游，负责把 DeepSeek 线协议收敛成 Harness 稳定流协议。

GenerateOptions + Message + Tools（输入）
                 │
                 ▼
LlmRuntime ─► Provider ─► DeepSeek HTTP/SSE
                 │               │ wire data
                 ◄──── StreamChunk 翻译
                 │
                 ▼
BlockAssembler ─► Message + Usage + Finish（输出）
                 │
                 ▼
              Session / Agent（下游）
背景与目的各模型的请求字段、SSE 帧和用量口径不同；核心运行时不应理解每家提供方的线协议。
输入与输出输入是模型、消息、工具、系统提示和取消信号；输出是内容增量、用量与唯一终止帧，最终组装成助手消息。
适用场景实时聊天、推理文本、模型工具调用、提供方替换、网络故障和取消。
底层组件异步生成器、AbortSignal、HTTP Fetch、SSE 增量解析器、提供方路由表和内容块组装器。
核心逻辑运行时选择提供方；适配器把任意网络切片还原成 SSE 载荷并翻译；组装器按块索引累计；模型步骤逐块落账并在终止时提交最终消息。
权衡统一协议无法暴露每个厂商的全部特性，但显著降低 Agent、存储和测试对提供方的耦合。
方案对比一次性等待完整响应实现简单但首字延迟高且难取消；直接透传厂商 SSE 灵活，却把不稳定协议扩散到所有下游。

场景穷举

一次模型流
├─ 文本/推理交错 → 按块索引组装
├─ 工具参数分片 → 保留并拼接原始 JSON
├─ usage 在末尾 → 先写用量，再写终止
├─ 网络异常/未知提供方 → 唯一 error finish
├─ 用户取消 → 唯一 cancelled finish
└─ [DONE] 无内容 → 正常闭合，不伪造消息
场景线协议现象框架语义
正常文本多个 SSE data 帧携带文本增量。开始、增量、结束、用量、终止顺序落账。
交错工具多个 tool call 的名称和参数按索引穿插。组装器为每个索引维护独立状态。
任意网络切片一个 SSE 行跨多个 Uint8Array，或一块含多帧。增量解析器按空行恢复完整事件。
提供方故障HTTP 非成功、JSON 错误或流中断。保留已收到块，只产生一个错误终止帧。
取消竞态取消与最后一帧同时到达。终止状态第一次写入获胜，不重复结束。

方案首字延迟统一性代价

关键设计反问

为什么必须只有一个终止帧？
Agent 和 Session 以终止帧决定步骤出口；重复或缺失都会导致双重结算或悬空生命周期。
为什么 usage 要放在 finish 之前？
消费者看到 finish 后通常停止读取；若用量在后面，它可能永远无法落账。
适配器应不应该重试？
只有在请求尚未产生可见输出且具备幂等条件时才可能安全；流已部分输出后自动重试会造成重复文本和重复副作用决策。

内容组装：三框架分别怎么做？

同一个问题：交错增量怎样成为完整模型消息？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
适配器把提供方 SSE 转换为 StreamChunk，块身份、增量与完成事件交给统一协议消费方。 依据 AIMessageChunk 支持累加，工具调用增量与消息内容在 LangChain 消息模型内组装。 依据 LLM 层处理提供方调用及流，Agent 解析结果形成 ActionEvent/MessageEvent；不是直接把网络帧当完整事件。 依据

这个概念的区别：组装需要保留内容块与调用身份，不能只拼 text 字段。

模型步骤落账：三框架分别怎么做？

同一个问题：流结束与写入完整消息是什么关系？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
成功调用恰好追加一个 assistant/message 锚点，包含 sourceEventSeqs 和可用 usage；空内容也有完成锚点。 依据 消息状态与检查点由图运行时保存，流订阅仅观察运行输出，不等于每个网络 chunk 已单独持久化。 依据 消息和行动作为 EventLog 事件保存，配置/统计另在 ConversationState；不要套用 DeepSeek 的 sourceEventSeqs。 依据

这个概念的区别：“前端看到字”不代表“完整模型步骤已持久化”，各框架的提交单位不同。

DeepSeek 请求适配：三框架分别怎么做？

同一个问题：接同一个模型 API 时谁做协议转换？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
deepseek-official 路由直接 fetch chat-completions；凭据按请求解析，另有 pi-ai 路径，二者可并存。 依据 使用支持工具调用的 LangChain 模型集成；模型参数和凭据应配置在该模型对象或 provider profile。 依据 通过 LLM/LiteLLM 的提供方适配调用；本课直接 fetch 的请求构造不是 SDK 的唯一入口。 依据

这个概念的区别：同一个供应商不代表同一套 harness 请求协议，配置应落在实际适配层。

DeepSeek SSE 翻译：三框架分别怎么做？

同一个问题：模型 SSE 和浏览器事件流是不是同一条通道？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
模型适配器用 eventsource-parser 分帧并翻译为 StreamChunk；这与浏览器侧双 WebSocket 下行是不同链路。 依据 模型集成处理提供方流，应用消费 LangChain 消息流/事件流；不必暴露提供方原始 SSE。 依据 LLM 流式调用与 Agent Server 的 HTTP/WebSocket 会话 API 分层；提供方格式不直接成为客户端协议。 依据

这个概念的区别：应分别画模型→运行时和运行时→界面两段传输，不能因为都有流就认为协议相同。

故障注入练习

  1. 让 Provider 输出一个 text delta 后抛异常，确认日志保留半截 chunk，但没有伪造 assistant/message。
  2. 把 Scripted Provider 延迟设为 1 秒，10ms 后 abort，观察 aborted finish。
  3. 删掉 SSE 的 [DONE]，确认 Adapter 报协议截断，而不是把半截响应当成功。
  4. 令 prompt_tokens=100、cache hit=40，确认 inputTokens=60，而非重复计为 100。
