背景与目的Promise.all 只能等待并发承诺，无法回答任务属于谁、怎样读流输出、父任务取消后谁负责收尸。
输入与输出输入是任务启动器、所有者、子智能体请求、工作流脚本和预算；输出是任务快照、流式文本、子结果、工作流结果及生命周期事件。
适用场景后台构建、并行代码调研、父 Agent 委派、扇出扇入工作流和有限资源池。
底层组件任务状态机、单消费游标、完成承诺、终止钩子、子智能体提供方、工作线程消息协议和并发信号量。
核心逻辑先验证能力与预算，再发布稳定运行标识；输出与状态集中进 Job；工作流只通过消息驱动子任务；任何超限或取消都沿所有权树向下收敛。
权衡集中控制面增加状态管理，却换来资源上限、隔离、可观测和确定清理；并发度限制会牺牲峰值速度以保护系统。
方案对比裸 Promise 适合短小同进程工作；作业队列适合持久分布式任务；本实现位于两者之间，专注单宿主可取消 Agent 编排。

场景穷举

并发工作
├─ 前台等待 Job → 流式读取 → completed
├─ 等待超时 → 只停止等待，Job 继续
├─ kill → producer.stop → stopping → 首个终态
├─ owner 释放 → kill + wait + remove 私有 Jobs
├─ Subagent 启动失败 → 不发布 start
├─ 父取消 → 向全部子运行传播
├─ Workflow 超并发 → 排队
├─ Workflow 超总数 → 拒绝并取消已启动子任务
└─ worker 忙循环 → 宽限后强制终止
场景控制面行为不变量
后台长任务Job 独立运行，调用方分段读取输出。只有一个消费游标，最终结果幂等。
多个所有者各自只能查看私有任务，共享任务所有人可见。任务标识不能泄露所有者信息。
子能力不匹配在 provider.start 前拒绝。没有伪造生命周期和外部资源。
扇出扇入并发限制内启动，等待所有需要的子结果。结果映射按脚本标识稳定关联。
部分失败脚本决定继续、降级或取消其余子任务。每个子运行仍独立闭合。
父级退出沿所有权树取消并等待。不能留下私有孤儿任务。

多方案对比

方案持久性控制能力适用场景
Promise.all仅进程内。基本等待，取消和所有权弱。短小同生命周期任务。
本地 Job/Subagent Runtime状态在进程内，结果可接会话日志。所有权、流输出、取消、预算完整。单宿主 Agent 并发。
持久作业队列跨进程重启。重试、租约和分布式调度。长任务和多节点。
工作流平台强持久。补偿、定时、人工节点。业务级长期流程，运维成本最高。

关键设计反问

等待超时为什么不取消 Job？
超时描述等待者的耐心，不代表生产任务应停止；把两者绑定会让旁观者意外终止共享工作。
为什么 start 事件必须在 provider 握手后发布？
发布即承诺存在一个可管理运行；握手失败前发布会留下无法取消、无法查询的幽灵子任务。
并发上限和总数上限有何不同？
并发上限控制瞬时资源，可排队；总数上限控制整个工作流爆炸，即使串行创建也必须拒绝。

后台任务创建：三框架分别怎么做？

同一个问题：启动返回 id 时，工作已经处于什么状态？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
jobs.start 先校验控制器、存活 owner 和容量，再调用生产方一次；预检或启动失败不生成 id。本地实现不排队，running/stopping 都占容量。 依据 start_async_task 创建服务端 thread/run，返回任务 id；可用 ASGI 同部署或 HTTP 远程传输，不一定跨进程。 依据 TaskToolSet 创建或恢复子会话并等待结果；它的 task_id 不是“已提交后台作业”的等价凭据。 依据

这个概念的区别：立即返回的作业句柄与同步工具最终结果是不同接口，不能仅按 task 命名对齐。

Job 状态机

start preflight ── run() throws ──► 无记录、id 不消耗
       │
       ▼
    running ── kill() 成功 ──► stopping
       │                         │
       └──────── done ───────────┘
                    ▼
          completed | killed | failed

wait timeout / wait Abort：只离开等待，不取消 Job
owner dispose：cancel → await done → 删除 private record

Job ID 是可预测的 <kind>-N，所以安全边界必须是 owner session 鉴权。unknown 与 foreign 返回相同错误，避免枚举侧信道。

任务输出：三框架分别怎么做？

同一个问题：重复读取输出，是增量消费还是重读最终结果？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
jobs.read 对流任务消费唯一游标，对最终输出任务幂等读取；get/list 只给非消费快照，多读者不能假设各有独立游标。 依据 check_async_task 查询状态，成功后从子 thread 状态提取最终输出；任务元数据另存 async_tasks，不依赖消息历史保留 id。 依据 TaskObservation 返回 task_id、subagent、最终 status 和 text，不是通用 stdout 流游标。 依据

这个概念的区别：界面展示进度、模型读取增量和收集最终答案需要分别选择接口。

任务状态机：三框架分别怎么做？

同一个问题：取消请求成功，是否等于工作已结束？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
kill 先调用生产方取消，成功才转 stopping；等待 done 结算后释放名额。取消抛错仍保持运行，首次终止结果只提交一次。 依据 取消经 runs.cancel，任务标为 cancelled；update 则在同一 thread 上中断旧 run 并创建新 run，任务 id 保持不变。 依据 TaskObservation 的 completed/error 是同步收集的最终结果，不提供与 running→stopping 相同的中间状态表。 依据

这个概念的区别：状态必须标明描述的是控制请求、某次 run，还是底层生产者完全停稳。

所有权：三框架分别怎么做？

同一个问题：谁能控制任务，谁销毁时负责清理？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
可预测 job id 不是授权；访问按 owner SessionId 隔离。生命周期清理绑定确切 Agent 对象，owner dispose 取消并等待，生产工具重载不结束任务。 依据 supervisor 的 async_tasks 记录其跟踪的子 thread；远程操作通过 Agent Protocol 服务鉴权，元数据归属不应被当作服务端访问控制。 依据 TaskManager 管理子会话并按 task_id 恢复上下文；公开工具指南没有建立 DeepSeek 确切 Agent scope 清理的等价契约。 依据

这个概念的区别：展示归属、访问权限和资源清理责任是三件事；知道 id 不能自动取得控制权。

任务等待：三框架分别怎么做？

同一个问题：等待者超时或取消，会不会停止生产任务？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
wait 超时返回存活快照，中止只停止等待；要停止任务必须 kill。已提交给等待方的终态优先于随后中止。 依据 异步委派让 supervisor 继续工作，通过 check/list 观察，cancel 是独立控制操作；不要把一次状态查询当成等待至终态。 依据 task 调用阻塞收集子会话结果；并行工具配置可改变多个调用的并发方式，但不把单次 task 变成轮询式后台接口。 依据

这个概念的区别：等待超时表达观察者的耐心；取消任务表达对生产者的控制，不应混用。

子 Agent 发布边界

  1. 检查 provider 是否存在、可用。
  2. 检查 output schema、深度、工具过滤、persona 是否被 provider 支持。
  3. provider.start() 完成握手并发布 child。
  4. 只有此时才发出 subagent/start。
  5. 任何终态归一为不会 reject 的 result，并发出唯一配对 subagent/end。
  6. dispose() 取消剩余工作并等待资源静止。

子智能体生命周期：三框架分别怎么做？

同一个问题：子任务完成后，能否继续给同一个子智能体发消息？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
一次性 start 发布 SubagentRun，由持有方收集并释放；startContinuable 在 inbox 接受后返回 childId/messageId，后续可冷恢复投递，不经普通 Job 结果 promise。 依据 异步子智能体保留自己的 thread，update 在同一 thread 发起新 run；这不同于每次调用都重新开始的同步委派。 依据 task 的 resume 参数重载已保存子会话继续处理，保留对话上下文；恢复调用仍同步收集结果。 依据

这个概念的区别：必须分别比较身份持续性与本次运行的收集方式；可恢复不等于始终后台驻留。

                                           │ result/null

脚本运行在独立 Worker Thread，因此死循环不会卡住 Host event loop。Worker 不是安全沙箱；脚本必须来自可信来源。取消先传播给所有 child，并等待 dispose；只有超过 cancelGraceMs 才强制终止。

工作流：三框架分别怎么做？

同一个问题：多步编排是否自动获得跨重启恢复？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
WorkflowEngine 接收动态脚本，持有方负责 dispose；限制并发、条目和子 agent 数，但不保存脚本进度与中间值，进程重启不能续跑。 依据 LangGraph 用节点、边和状态表达顺序、并行及路由；配合持久 checkpointer 才形成恢复基础，不是动态脚本自动持久化。 依据 TaskToolSet 支持委派与子会话恢复；若应用要多阶段流程、重试与补偿，仍需另行编排，不能把子会话保存当成整个流程检查点。 依据

这个概念的区别：保存子任务历史、保存编排进度、回滚外部副作用是三个不同等级的能力。
