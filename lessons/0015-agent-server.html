完整能力清单

能力完整行为网络边界
持有者鉴权在任何 RPC 分派、事件读取或附件访问前验证 Bearer 令牌。未授权请求不能探测会话是否存在。
RPC 控制面创建、恢复、发送、运行、取消、快照和关闭会话，返回稳定结果或错误。严格校验请求结构和方法参数。
请求幂等按请求标识缓存同一命令结果，支持客户端安全重试。同一标识绑定不同命令时报冲突。
多会话路由以会话标识定位独立宿主和运行状态，并隔离并发命令。同一会话运行中再次发送被忙碌错误拒绝。
SSE 数据面从指定序号重放历史后追尾实时事件，SSE 事件标识等于 Session 序号。客户端可凭最后序号无缝续传。
资源预算限制 RPC 请求体和 SSE 单帧大小，并处理慢消费者。请求超限返回 413，帧超预算主动断开。
恢复与停机服务关闭时取消运行、关闭连接、刷盘并释放宿主；新服务可冷恢复。网络层不是恢复事实源。
同源网页与附件可挂载静态网页、附件上传和鉴权读取入口。静态路径防逃逸，API 始终保留鉴权。

主概念深挖：Agent 网络服务层

Agent Server 的上游是 CLI、Web 和 SDK 客户端，下游是 Headless Host 与 Session；它把进程内用例扩展成经过鉴权、路由、幂等和背压控制的网络协议。

Client（Bearer、requestId、command）
       │ JSON-RPC 控制面（输入）
       ▼
Auth ─► Idempotency ─► Session Router ─► HeadlessHost / Agent
                                         │ append events
                                         ▼
Client ◄──── SSE 重放 + 追尾（输出） ◄── Session Log
       │ after=lastSeq
       └─ 断线后续传
附件与静态网页走独立路由，但共享鉴权和路径边界
背景与目的进程内 Agent 没有网络身份、请求重试或慢客户端问题；一旦提供远程访问，这些就成为独立且不可省略的服务层职责。
输入与输出输入是 Bearer 令牌、RPC 方法、请求标识、参数和 SSE 游标；输出是 RPC 结果/错误、连续事件帧及 HTTP 状态。
适用场景网页客户端、远程 SDK、多会话守护进程、断线重连和客户端重试。
底层组件Bun HTTP Server、RPC 分派、令牌校验、幂等缓存、会话宿主映射、SSE 编码、请求与帧预算。
核心逻辑先鉴权再解析命令；requestId 绑定命令摘要和结果；路由到会话宿主执行；事件先按序号重放，再订阅追加；关闭时停止接入并刷盘。
权衡RPC 与 SSE 双通道比单 WebSocket 更容易分别重试和缓存，但需要管理两个连接语义。
方案对比REST 轮询简单但延迟和流量高；WebSocket 全双工灵活但恢复协议更自定义；RPC+SSE 利用 HTTP 语义并以 Session seq 天然续传。

场景穷举

网络请求
├─ 无/坏 Bearer → 分派前 401
├─ 新 requestId → 执行并缓存结果
├─ 同 id 同命令重试 → 返回相同结果
├─ 同 id 不同命令 → 冲突
├─ session busy → 拒绝并发命令
├─ SSE after=N → 重放 N+1..末尾 → 实时追尾
├─ 慢消费者/大帧 → 断开保护服务
├─ 请求体超限 → 413
└─ shutdown → 停接入、断流、取消、flush、dispose
场景控制面数据面
首次发送RPC 返回接受或轮次结果。SSE 按 Session seq 推送事实事件。
响应丢失重试相同 requestId 返回缓存结果。不会产生第二组事件。
SSE 断线无命令状态变化。客户端以 lastSeq 重新连接并补齐。
多会话路由到独立 HeadlessHost。订阅只接收目标 Session。
冷重启新宿主按 id 恢复。历史从持久日志重放，不从旧连接恢复。
恶意输入鉴权、结构和体积检查先于领域调用。帧预算防止单事件拖垮缓冲区。

协议命令事件流恢复复杂度
REST+轮询标准。延迟高、重复传输。低。

关键设计反问

为什么鉴权必须早于“会话不存在”判断？
否则未授权调用者能通过响应差异枚举有效会话标识。
为什么 requestId 还要绑定命令摘要？
只按 id 缓存会让客户端错误复用 id 时拿到无关旧结果，掩盖严重调用方缺陷。
SSE 慢消费者为什么可以被断开？
事件已有持久日志，客户端可按序号重连；无限为单连接缓存反而会拖垮所有会话。

RPC 控制面：三框架分别怎么做？

同一个问题：客户端方法怎样映射到服务端能力？

SSE 数据面：三框架分别怎么做？

同一个问题：浏览器持续接收事件的实际协议是什么？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
上游使用 events.mux 与 events.host 两条只下行 WebSocket；网络 GET 返回 426，没有 SSE 回退。Fetch SSE 编解码只供进程内载体，本课 SSE 是教学方案。 依据 部署 Streaming API 提供状态、更新、消息等流模式，thread stream 可用最后事件 id 重连；其流不是 DeepSeek Session 原始日志格式。 依据 Agent Server 提供 HTTP 与 WebSocket 会话事件 API，不能因为本课标题为 SSE 就把其传输也描述为 SSE。 依据

请求幂等：三框架分别怎么做？

同一个问题：超时重发一次请求，会不会执行两次？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
Gateway 的描述符和类型校验约定不等于持久去重承诺；本课 requestId 缓存是教学机制，不能从上游 Remote 方法生成推断同样保证。 依据 服务端对运行中再次提交可选择拒绝、入队、中断或回滚；这些 double-texting 策略处理重叠运行，不等于重复 HTTP 请求的幂等键。 依据 服务概览列出了会话与命令 API，但没有声明通用 requestId 去重协议；客户端不得仅因调用远程 Conversation 就假设写请求可安全重试。 依据

这个概念的区别：需分别检查重复提交去重、并发运行策略和外部工具副作用；任一层成立都不能替代另两层。

恢复在哪里发生

session.resume 通过 HeadlessHost 调用 Session Store：checksum、torn-tail repair、interrupted closer、投影重放，再发布 active Conversation。Agent Server 的幂等缓存、SSE 连接和 live Agent 都是易失控制状态，不是恢复源。

恢复与停机：三框架分别怎么做？

同一个问题：连接恢复与运行恢复分别发生在哪一层？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
任一事件 socket 结束都会使 generation 失效并重建双流；Host teardown 中止 source 并等待清理。会话冷恢复另由持久化/Agent 层完成，不由 socket 重连代替。 依据 流重连按最后事件 id 补收事件；执行恢复依赖检查点。重新连接已有 run 的流，不是再次提交同一个任务。 依据 会话从持久数据恢复，服务端敏感值需保持 OH_SECRET_KEY 才能解密；网络重新连通不证明旧运行或外部进程仍存活。 依据

这个概念的区别：停机需明确停止准入、运行收敛与存储完成；重连成功只能证明传输恢复。

背压与停机

  • SSE 每个连接有独立字节队列；单帧或积压超预算立即断开慢消费者。
  • res.write() 返回 false 时等待 drain/close，不无限写入内存。
  • Server close 先停止接收和关闭 SSE，再取消 running Agent，flush/close conversations，最后 dispose Host。

资源预算：三框架分别怎么做？

同一个问题：请求、运行和执行环境的上限由谁控制？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
Connection 整体缓冲请求体，maxRequestBodyBytes 限制单请求驻留内存；这是传输预算，不替代工具输出、任务并发等能力预算。 依据 异步子任务占服务 worker 槽，槽不足会排队；并发工作数属于部署容量，不是模型上下文窗口或 token 预算。 依据 LocalWorkspace、DockerWorkspace 和远程工作区使用不同执行环境；CPU/内存隔离应查实际容器或服务配置，不能从 SDK 的工作区抽象推定已设限。 依据

这个概念的区别：至少分别验收入口内存、运行并发和执行资源；一个 max 值不能覆盖整条链路。
