主概念深挖：可证明的崩溃恢复

持久化层位于 Session 内存账本的下游、宿主恢复与 Agent 续跑的上游；它只恢复磁盘上可以通过字节和协议证明的事实。

Session.append(event)（输入）
        │ 串行 write-behind
        ▼
Header + JSONL + checksum ── flush/fsync ─► 磁盘事实
                                             │ 冷启动
                                             ▼
字节检查 ─► 半行截断 ─► 生命周期补闭合 ─► Session
                                             │
                                             ▼
                                  投影重建 + Agent 续跑（输出）
背景与目的进程可能在任意字节位置死亡；恢复若猜测未提交数据或重试未知副作用，会把一次崩溃变成重复破坏。
输入与输出写入输入是会话头和连续事件；恢复输入是原始文件字节，输出是校验后的 Session、修复事件和下一轮编号。
适用场景服务重启、机器掉电、CLI 跨进程继续、历史分叉和损坏诊断。
底层组件JSONL、校验和、换行提交标记、串行写后队列、fsync、序号校验、生命周期修复器和安全文件名编码。
核心逻辑换行定义记录提交边界；完整记录必须逐条通过校验和与序号检查；仅未换行尾部可截断；悬空工具写未知结果而非重试。
权衡每行校验和与频繁刷盘增加 I/O 成本，却能区分未提交尾部和已提交损坏，并提供明确耐久边界。
方案对比数据库提供事务与索引但引入服务和迁移复杂度；JSONL 易检查、易教学、适合单会话顺序写，规模增长后可换后端而保留协议。

场景穷举

冷恢复读取文件
├─ 全部行完整且校验通过 → 直接重建
├─ 最后一段无换行 → 截断到最后提交边界
├─ 完整行 checksum 错 → 拒绝恢复
├─ seq 缺口/重复 → 拒绝恢复
├─ open tool call → UNKNOWN result + closers
├─ open step/turn → interrupted closers
└─ fork at seq → 补边界 + parent lineage + 独立日志
崩溃位置磁盘证据恢复决定
写入前没有新字节。事件未提交，不存在。
写到半行末尾无换行。安全截断半行。
完整行后、fsync 前可能存在也可能随掉电丢失。以实际可读完整行作为事实；flush 才承诺耐久。
工具副作用后、result 前只有 tool/call。写 UNKNOWN，要求检查外部状态。
修复事件写到一半修复尾部也遵循换行边界。下次恢复再次确定性生成相同 closers。
历史中间损坏完整坏行或序号缺口。停止，绝不自动跨过。

关键设计反问

为什么换行能当提交标志？
写入器承诺每条记录只有完整编码后才追加换行；因此无换行尾部一定不是已提交记录，而完整行必须接受校验。
为什么不能自动重跑悬空工具？
外部写操作可能已经成功，只是 result 未落盘；自动重跑可能重复付款、删除或覆盖。
flush 是否保证所有存储硬件场景绝不丢失？
它提供操作系统和文件系统暴露的耐久屏障，不等于对故障硬件作绝对保证；真正生产还需磁盘、复制和备份策略。

文件格式

{ kind: "header", header: { id, format, version, cwd, parent? }, checksum }
{ kind: "event",  event:  { seq: 0, type, time, data },       checksum }
{ kind: "event",  event:  { seq: 1, type, time, data },       checksum }
...
情况处理原因
最后一段没有换行截断到最后完整换行writer 永远以换行提交记录，它是 torn tail
完整 JSON 行 checksum 错拒绝恢复这是已提交数据损坏，不能猜测
seq 有缺口拒绝恢复无法证明中间事件语义
open turn/step追加 deterministic closer提供可继续的协议闭包
tool/call 无结果TOOL_OUTCOME_UNKNOWN外部副作用可能已经发生

恢复顺序

read bytes
  → 找 committed newline prefix
  → 校验 header identity/version/checksum
  → 校验每条 event checksum + seq
  → fsync 截断 torn tail
  → 合成 tool/result / step/end / interrupted turn/end
  → fsync closers
  → 构造 Session
  → 重放 messages / usage / permissions / lifecycle 投影
  → Agent 从 max(turn)+1 继续
未知副作用不能自动重试。如果 tool/call 已持久化而 result 没有，恢复只能声明 TOOL_OUTCOME_UNKNOWN。读操作或幂等操作可评估后重试；写操作必须先检查外部状态。

生命周期修复：三框架分别怎么做？

Flush 与骤停

Session.append() 进入串行 write-behind 队列；flush() 等待队列并调用文件 fsync。测试用独立 Node 子进程 flush 后直接退出，再由父进程冷恢复，证明耐久边界不是同进程缓存假象。

写后队列与刷盘：三框架分别怎么做？

同一个问题：哪个边界之后才允许认为状态已持久化？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
协调器按会话批量排队；session/flush 取消合并等待并排空，JSONL 后端 append 后 fsync。内存 append 与持久屏障不同。 依据 durability 可选 sync、async、exit：分别在下一步前完成保存、与下一步并行保存、退出时保存。选项影响进程崩溃时可恢复的位置。 依据 ConversationState 字段变更自动保存基础状态，事件增量写文件；公开使用方式不是调用本课的 Session.flush。是否等价于特定硬件耐久屏障须另查底层实现。 依据

这个概念的区别：DeepSeek 暴露 flush 屏障，LangGraph 暴露执行耐久策略，OpenHands 提供自动保存；自动保存不等于已经证明 fsync 语义。

Fork

source events[0..atSeq]
  → 如果切在 turn 中间，补 interrupted closers
  → 新 header.parent = { sessionId, seq }
  → 写入独立 JSONL
  → 后续 append 互不影响
