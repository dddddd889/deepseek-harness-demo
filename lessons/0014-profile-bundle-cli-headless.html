第 14 课：Profile、Bundle、CLI 与 Headless Host

同一套 Runtime 不应为 CLI、测试和未来 Web Server 各装配一次。本课建立稳定 composition root：Profile 决定部署数据，Bundle 决定插件图，Host 提供用例 API，CLI 只翻译进程协议。

主概念深挖：组合根与无界面宿主

Headless Host 位于部署配置和插件包的下游、CLI、Agent Server 与测试的上游，是所有产品入口共享的唯一装配根。

默认值 → 配置文件 → 环境变量 → CLI 覆盖（输入）
                       │ validate Profile
                       ▼
                  HeadlessHost.open
          ┌────────────┼────────────┐
          ▼            ▼            ▼
     SessionStore   LlmRuntime   HarnessBundle
          └────────────┼────────────┘
                       ▼
          Conversation 用例 API（输出）
              ┌────────┼────────┐
              ▼        ▼        ▼
             CLI   Agent Server  Tests（下游）
背景与目的如果 CLI、服务端和测试分别初始化存储、模型与插件，它们会悄悄形成不同语义，恢复和释放问题难以复现。
输入与输出输入是分层 Profile、可选提供方覆盖和交互中介器；输出是创建/恢复会话、运行/取消轮次及关闭释放的用例接口。
适用场景命令行工具、后台服务、集成测试、嵌入式 SDK 和本地演示。
底层组件严格配置解析器、固定覆盖优先级、HarnessBundle、JSONL 存储、LlmRuntime、HeadlessConversation 和信号处理。
核心逻辑Profile 只描述部署数据，Bundle 只描述插件图，Host 负责实例化与所有权，CLI 只翻译 argv/stdin/stdout，不复制领域逻辑。
权衡统一组合根减少入口自由度，却防止配置漂移和生命周期分叉；严格拒绝未知字段会降低向前兼容的宽松度。
方案对比框架式全局容器方便自动注入但隐藏装配顺序；显式组合根代码更直白，适合调试和证明资源所有权。

场景穷举

启动产品入口
├─ 默认配置 → 校验 → 新建会话
├─ 文件+env+CLI → 固定优先级覆盖
├─ 未知字段/坏枚举 → 装配前失败
├─ Bundle 第 N 个插件失败 → 逆序回滚 1..N-1
├─ --session → 创建并持久化
├─ --resume → 冷恢复并继续
├─ --interactive → 同一会话逐行运行
├─ SIGINT → 取消当前轮次
└─ close → 刷盘、卸载、退出码
场景输入来源宿主行为
本地开发Profile 文件+环境密钥。创建真实提供方和工作区会话。
离线测试脚本提供方覆盖。不访问网络，复用同一 Host 语义。
跨进程恢复新进程仅提供 session id。从持久化根重建，不依赖旧 Agent 对象。
配置冲突文件、env、CLI 同时给模型。CLI 胜出，并可通过 dump/config 证据解释。
关闭竞态轮次仍运行时收到退出。先取消运行，再刷盘并释放 Bundle。

关键设计反问

为什么 Profile 不直接创建对象？
Profile 应是可校验、可打印的部署数据；若混入对象工厂，就无法通过 JSON 配置、比较或安全输出。
为什么 CLI 不直接操作 HarnessAgent？
那会复制存储、恢复和释放逻辑；CLI 应只依赖稳定用例 API，使服务端和测试共享同一语义。
未知配置字段为什么要拒绝？
宽松忽略会把拼写错误变成静默使用默认值，尤其可能导致错误模型、目录或沙箱策略。

命令行：三框架分别怎么做？

同一个问题：一次性任务入口何时输出并退出？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
dsh --profile headless 接收一个任务，创建新持久 Agent，等待停稳并 flush 后输出最后非空 assistant 文本；完成退出 0，否则 1，没有交互式后续输入。 依据 Deep Agents Code 是独立命令行产品入口；库的 create_deep_agent 不是 argv 解析器，CLI 行为应按该产品文档核对。 依据 SDK 可由 Python脚本创建 Conversation、发送消息并 run；参数解析、终端格式和退出码属于使用 SDK 的入口程序，不能从 Conversation API 推导统一 CLI 约定。 依据

这个概念的区别：本课交互输入和 JSONL 输出是实验室入口能力，不应直接归给三套框架的所有命令行产品。

配置合并：三框架分别怎么做？

同一个问题：多个来源给出同一设置时，实际按什么规则合并？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
settings 按 schema 默认值、组合 base、用户分节解析；update 深合并用户层并先校验再持久化。不是本课默认值→文件→环境→CLI 的通用四层算法。 依据 模型级 Profile 覆盖提供方级；具体字段分别采用标量覆盖、集合并集、字典逐键合并和中间件按名称合并，不是统一替换。 依据 AgentSettings 使用 Pydantic 校验配置数据；旧持久化配置经 from_persisted 迁移。该接口不定义本课那套文件/env/CLI 优先级。 依据

这个概念的区别：合并与迁移是不同问题；覆盖顺序还不足以说明集合、嵌套对象和未知字段的行为。

配置模型：三框架分别怎么做？

同一个问题：配置描述整个应用，还是只描述模型与 Agent？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
插件分别注册 settings namespace，持有 schema 与组合 base；配置按能力归属，不是单个 Profile 对象拥有全部运行时资源。 依据 HarnessProfile 调整提示词、工具和中间件；ProviderProfile 负责模型构造参数。运行时实例与可序列化 HarnessProfileConfig 也分开。 依据 OpenHandsAgentSettings 描述模型、工具和 condenser 等 Agent 配置，可序列化后重建；并不代表已创建 Workspace 或运行会话。 依据

这个概念的区别：先明确配置对象覆盖范围，再决定哪些字段可保存、哪些资源必须重新创建。

Headless 恢复路径

process A: --session stable task-1
  create → Agent turn 1 → flush/fsync → close/dispose

process B: --resume stable task-2
  checksum/repair → Session replay → Agent nextTurn=2
  → flush/fsync → close/dispose

独立进程测试验证了这条路径；它不是同一进程里复用内存对象的“伪恢复”。

会话用例：三框架分别怎么做？

同一个问题：创建、发送与恢复由哪个公开对象承接？

DeepSeek Harness 原实现LangChain DeepAgentsOpenHands SDK
ctx.agents 管理创建和恢复，Agent 接口提供消息与运行控制；Session 存事件，持久化是另一服务，不是让入口直接改事件数组。 依据 调用图时以 thread_id 关联检查点；新输入调用与 Command(resume=...) 恢复 interrupt 的语义不同。 依据 Conversation 承接 send_message/run 等操作并协调状态、事件与 Agent.step；Agent 本身不是会话存储容器。 依据

这个概念的区别：迁移入口时映射用例而不是类名：发新消息、继续暂停与重建进程内对象不能混成一个 resume。

独立进程恢复：三框架分别怎么做？
